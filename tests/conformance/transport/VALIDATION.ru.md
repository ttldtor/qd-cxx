# Проверка осуществимости профиля runtime

[English version](VALIDATION.md). Авторитетной является английская версия.

Область: [ADR-0006](../../../docs/decisions/ADR-0006-live-runtime.ru.md) и [T01–T14](CONTRACTS.ru.md).
Результат выбирает осуществимые механизмы SDK и фиксирует явные требования к интеграции. Он не реализует и не квалифицирует production-клиент runtime/session/TLS/auth.

## Нативные профили на финальном исходном коде

| --- | --- | --- | --- |
| Windows x64, MSVC 19.42.34444, Release, Ninja | CTest 1/1 | CTest 2/2 | Native Release; существующий consumer по умолчанию `/MD` сохранён. |
| Ubuntu 24.04 x86-64, GCC 13.3, Debug, Ninja | CTest 1/1 | CTest 2/2 | ASan+UBSan, `detect_leaks=0:halt_on_error=1`, остановка при UBSan; инструментированы DNS C SDK и C++ runner, отдельно собранный OpenSSL SDK не инструментирован. |

[Lock DNS](runtime-feasibility/dns/dependencies.lock.json) закрепляет исходный архив c-ares 1.34.9 и квалифицированный патч `1.34.9+qdcxx1`; повторное применение без fuzz воспроизвело все 532 хэша исходных файлов. Оригинальный upstream сохранён отдельно. [Lock TCP/TLS](runtime-feasibility/tls/dependencies.lock.json) закрепляет Asio 1.38.2 и OpenSSL 3.5.9. OpenSSL статически собран из исходников с assembly и `no-autoload-config`; проверены экспортированный macro и версии компиляции/runtime. Хэши исходников/архивов и опубликованные контрольные суммы сверены; независимая проверка PGP не выполнялась.

## Наблюдения

- DNS: восемь отказов на невалидной конфигурации и 24 wire-сценария для каждого нативного профиля: двадцать отмен ожидающих запросов с повторным использованием, два уничтожения канала с ожидающим запросом и два случая квоты приёма/возобновления. Принадлежащие стенду UDP/TCP-peers получают точный вопрос `hold.invalid.` до вывода из эксплуатации. Каждый ожидаемый completion происходит ровно один раз на потоке-владельце со статусом `ARES_ECANCELLED` или `ARES_EDESTRUCTION`, без оставшихся fd и последующих callbacks в течение конечного периода наблюдения. Более сильная граница уничтожения также опирается на доказательства из исходников/API SDK; короткое наблюдение само по себе не доказывает поведение для любого будущего времени.
- UDP отправляет шесть пакетов с несовпадающими transaction ID, затем NXDOMAIN: не более двух native read/двух датаграмм за проход SDK, три уступки по квоте, затем один `ARES_ENOTFOUND`. TCP сохраняет частичный ответ между чтениями по семь байт и завершает операцию один раз после возобновления. Это управляемые конечные нагрузки, а не продолжительное испытание враждебной сети или универсальный бенчмарк задержки.
- Квалифицированный патч отклоняет отсутствующую/чрезмерную/нулевую конфигурацию серверов до выделения канала, исключает системные настройки, env/NSS и fallback на hostname/default server, а на reinit возвращает `ARES_ENOTIMP`. Враждебное значение `RES_OPTIONS=use-vc` в дочернем процессе не изменило явный UDP-сценарий. Неверный стандартный SDK отклоняется; канал без event thread не владеет DNS worker или монитором конфигурации.
- Проверка TCP connect отдельно учитывает немедленные гонки отмены и действительно ожидающие соединения. В fixture с loopback backlog на 512 соединений оставались ожидающими и были прерваны 312 операций в Windows и 510 в Linux; все отправленные completion дренированы. Ожидающие чтения и записи в адрес не читающего peer оставались незавершёнными до отмены; частичная запись не означает подтверждение peer.
- Положительные случаи TLS согласуют версии 1.2 и 1.3 с DNS SAN/SNI и идентичностью IP SAN. Неизвестный issuer, неверное имя хоста и просроченный сертификат отклоняются с X509-кодами 20, 62 и 10; неуспешные handshake не сообщают о согласованной сессии. Зависшие handshake и graceful shutdown отменяются закрытием нижнего уровня, а handlers дренируются до уничтожения stream/context/provider/library-context/host.
- Проверенные TLS-контексты применяют ограничение Certificate message 64 KiB, глубину проверки 4, явные record buffers Asio по 17 KiB, отключённые сжатие записей/сертификатов и renegotiation. Полная production-политика допуска ключей/group/SPKI/trust и бюджет памяти/работы SDK остаются требованиями реализации; обычные сертификаты RSA-2048 не доказывают отклонение всех ключей чрезмерного размера или враждебных ключей.
- Helper таймеров Windows IOCP виден в измеренном количестве потоков процесса: 4 → 5 → 4; Linux epoll остаётся 1 → 1. Эти числа относятся к данным процессам и не являются универсальными базовыми значениями ОС. Stop запрашивается из сериализованного completion; оставшиеся completions обрабатываются до внешнего уничтожения host.
- Probe-consumers Windows `/MD` и `/MT` оба линкуются и запускаются с одним статическим OpenSSL SDK `/MT /Zl`. Upstream-конфигурация намеренно подавляет определённую ссылку на RTL; импорты `/MD` проверены, DLL OpenSSL не потребовалась. Политика root CRT и глобальное окружение не менялись.
- Вывод без аргументов/`--help` одинаковый, непустой, код завершения 0, stderr пуст. Невалидные аргументы и отсутствующие fixtures приводят к ошибке. В Linux `/dev/full` подтверждает ненулевой результат при ошибке вывода справки. Справка не генерирует ключи, не открывает тестовые сокеты и не требует входных fixtures. DNS executable — внутренний no-argument CTest runner.
- Оба отдельных проекта проходят configure/build с настройкой OFF по умолчанию и отсутствующим SDK; поиск компилятора/SDK и сетевое получение пропускаются. Это ничего не доказывает о будущих production-параметрах, которых ещё нет. Обычные root source/targets этим решением не менялись.

## Факты по исходникам, ограничения и отложенная работа

Стандартный Asio DNS использует блокирующий resolver worker; уничтожение event thread стандартного c-ares может присоединить работу системной конфигурации; стандартный c-ares с ручным управлением может бесконечно обрабатывать UDP. Это выводы по закреплённым исходникам, а не выдуманные испытания зависшей ОС. Квалифицированный вариант с управлением со стороны вызывающего кода и socket quotas отвечают выбранным механизмам. Доступность нативных криптографических служб ОС и согласование bootstrap на уровне процесса остаются явными требованиями; гарантия реального времени не выводится.

Хранилище SDK включается в контракт ресурсов. [Профиль DNS](runtime-feasibility/dns/profile.json) фиксирует консервативный envelope входного буфера/перевыделения, а не полный измеренный heap SDK. Начальное декодирование DER/ключа в TLS может происходить до callback проверки; перед полным заявлением о ресурсах адаптера следует ограничить входы и учесть эту работу. Общие пользователи SDK должны соблюдать документированные ограничения bootstrap, allocator, глобальной конфигурации SSL и пользовательских ENGINE/key methods.

Независимое критическое ревью и повторные нативные проверки относятся к этому ограниченному результату осуществимости. Барьеры callbacks production session/adapter, порядок auth с реальным состоянием протокола, полные envelopes SDK, замыкание зависимостей consumer package/install, reconnect, изоляция между run, враждебные случаи DER/key, продолжительная нагрузка и внешние развёртывания остаются отдельными обязательными доказательствами интеграции. Регрессии native root и Doxygen публичного API из прежних ревизий реализации не переименовываются в новые транспортные тесты; публичный production API и параметры сборки root здесь не менялись.

## Граница квалификации рабочего TLS

Исторические профили механизмов/SDK выше сохраняют исходные входы и область доказательств.
Они не исполняют новый TLS runtime и не доказывают его контракт ресурсов всего запуска, учётных
данных и callbacks. Текущая [валидация ресурса/runtime TLS](TLS-VALIDATION.ru.md) отделяет настоящие
чистые native-тесты ресурса, ограниченные проверки runtime, обычного повреждённого ввода/политики
ключей, пакета/сборки без TLS, потребителя и открытые итоговые проверки интеграции.
[Ресурсный контракт](../../../spec/transport/TLS-RESOURCES.ru.md) добавляет условия контролируемой
истории общего экземпляра OpenSSL и именованного вектора. Он не считает отдельный контекст
библиотеки и измерения выполнимости полным пределом ресурсов SDK.

### Текущая граница доказательств TLS

Рабочий TLS runtime реализован. Целевой набор текущих исходников прошёл 39 native-тестов: Windows MSVC 19.42 x64 Release /MD — 11 486 проверок; Linux GCC 13.3 x64 Debug ASan+UBSan — 11 625 проверок, LSan выключен. Полная регрессия на каждой ОС прошла 58/58 тестов с JSON и 57/57 без JSON. Проверка сгенерированной справки учитывается отдельно. Обновлённый установленный пакет прошёл четыре TLS 1.2/1.3 запуска на двух ОС. Результаты отдельных проверок не означают выпуск, полную поддержку подписок или сертификацию безопасности. Актуальный перечень выполненных и только обоснованных исходниками случаев находится на странице квалификации TLS, ссылка на которую приведена выше.
