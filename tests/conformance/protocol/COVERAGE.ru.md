# Покрытие C++ framing conformance

[English version](COVERAGE.md). Английская версия является нормативной.

[Контракт](../../../spec/protocol/FRAMING.ru.md), [реализация тестов](../frame_tests.cpp),
[валидация](VALIDATION.ru.md). Все 18 выбранных входов обязательны; исключений нет.

## Независимые ожидания и расписания

[frames.tsv](frames.tsv) — проверенная **производная проекция только кадров**, не вывод callbacks Java.
Байты читаются непосредственно из неизменного [P01](../../fixtures/protocol/expected/P01.tsv) и нового
[P02](../../fixtures/protocol/expected/P02.tsv). Зафиксированные границы/type P01 задают три непрозрачных
среза payload. Границы/ширины type P02 проверены по точному входу, hooks/позициям Java, классификации
ошибок и [контракту со ссылками на исходники](../../../spec/protocol/FRAMING.ru.md).
Production decoder не генерировал ожидания. Столбцы содержат лимит body, упорядоченные
kind/type/payload/start/end, первую framing-ошибку C++, accepted, pending hex и error offset.
`-` означает отсутствие кадров/type либо пустые байты в соответствующем поле.

P02 empty и explicit-zero различаются. Unknown 62 и повреждённый heartbeat payload выдаются непрозрачно;
выделение прекращается только при framing-ошибке. Java может восстановиться после ошибок type/body;
проекции C++ останавливаются на первой framing-ошибке. Диагностическое потребление Java при неверной
длине не переносится в accepted.

Каждый вход проверяется целиком, при каждом разбиении на две части с пустыми краями, побайтно с
пустыми feed и при **каждом разбиении на три части** с добавленными пустыми feed. Каждый вызов
проверяет accepted, отсутствие преждевременной выдачи, точный сохранённый суффикс, постоянный размер
буфера, порядок выхода и терминальное поведение. Ранее выданные кадры повторно проверяются после
следующих feed и reset. Для finish проверяются чистый/усечённый/ошибочный вход, идемпотентность и
отказ принимать последующий ввод.

## Ресурсы, границы и владение

- 10 000 трёхбайтовых кадров в одном входе из 30 000 байт при буфере reader 11 байт. Каждый feed
  принимает/выдаёт ровно один кадр; непринятый суффикс принадлежит вызывающему. Очереди выхода нет.
- Сохранённый payload переживает следующие feed/reset и отдельно уничтожение reader.
- Несовместимые бюджеты pending/body и переполнение на максимуме size_t отклоняются до выделения.
- Нулевой бюджет body разрешает пустой heartbeat и отклоняет ненулевой body.
- Девятибайтовые overlong length и type точно заполняют reader на 18 байт; каждый строгий prefix
  сохраняется без изменения и не выдаёт кадр раньше времени. Полный type равен нулю.
- Type INT_MAX принимается; длина INT64_MAX превышает малый бюджет body, INT64_MIN нарушает
  проверку знака; обе отклоняются после девяти байтов prefix без огромного выделения.
- PART type 4 с выглядящим некорректно payload выдаётся непрозрачно, без сборки/декодирования.

Три doctest cases выполняют 246 166 assertions. Прежние четыре primitive cases добавляют 43 375
assertions, покрывая все 832 compact и 314 UTFString наблюдения Java без исключений. Negative runner
отклоняет изменённый ожидаемый байт payload, неверный hex входа, отсутствующий выбранный вход,
пустой набор P02 и пустые проекции; подтверждается неизменность исходных и временных fixtures.

## Ограничения

API однопоточный, concurrency stress отсутствует. Огромные выделения, инъекция allocation failure,
исчерпание uint64 потока, 32-битная платформа, macOS, другие Java buffers, payload decoding, матрица
политик adapter, запись кадров, сборка PART и transport не проверялись. Исключение выделения в
конструкторе и терминальная ошибка выделения payload являются документированными контрактами,
а не результатами инъекционных экспериментов. Benchmark и полная совместимость QTP не заявляются.
