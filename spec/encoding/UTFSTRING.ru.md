# Контракт ограниченного C++ UTFString

[English version](UTFSTRING.md). Английский документ является основным.

QDCXX-011 реализует утверждённую ограниченную политику поверх неизменных
[свидетельств Java QD 3.355](PRIMITIVES.ru.md). API: [utf_string.hpp](../../include/qd/encoding/utf_string.hpp).
Это только UTFString, а не общий API преобразования Unicode.

## Представление и время жизни

`readUtfString(span<const byte>, UtfStringLimits)` возвращает `UtfStringResult` с `status`,
`consumed` и `optional<u16string> value`. Значение интерпретируется только при `OK`: отсутствие
означает Java null; присутствующая пустая строка означает empty. При любой ошибке значение
отсутствует. Результат владеет единицами UTF-16. `writeUtfString(optional<u16string_view>, span<byte>,
UtfStringLimits)` заимствует вход и выход только на время вызова; их память не должна пересекаться.
Нет переинтерпретации wchar_t, нормализации, символов замены или исправления суррогатов.

Каноническая запись сохраняет отдельные суррогаты как трёхбайтовые единицы, а корректные пары
объединяет в четырёхбайтовые кодовые точки. Чтение сохраняет точные единицы, принимая измеренные
overlong/CESU-формы. Null — compact long -1, empty — ноль. Остальные префиксы считают байты тела,
не единицы UTF-16. Все префиксы обрабатывает существующий compact codec без изменения его поведения.

## Ошибки, позиции и ресурсная политика

Вызывающая сторона обязана передать оба конечных бюджета `size_t`: `bodyBytes` и `codeUnits`.
Нет аргумента по умолчанию или специального неограниченного значения. Это эксплуатационные лимиты,
а не ограничения Java wire или гарантия точного объёма памяти аллокатора. Нулевые бюджеты допускают
null и empty.

Приоритет чтения:

1. Неполный compact-префикс: `INSUFFICIENT_INPUT`, потребляется переданный префикс.
2. Длина вне -1..8589934588: `INVALID_LENGTH`, после префикса.
3. Null успешно возвращается; иначе превышение бюджета байтов тела даёт `RESOURCE_LIMIT` после
   префикса, без просмотра тела и выделения памяти пропорционально объявленной длине.
4. Как Java, сначала прочитать весь хвост символа, затем проверить continuation bits. Отсутствующий
   хвост даёт `INSUFFICIENT_INPUT` в конце span; неверный lead/tail или точка выше 0x10FFFF даёт
   `INVALID_ENCODING`. Overlong-кодировки и суррогатные кодовые точки принимаются.
5. Перед добавлением единицы/пары проверить полный бюджет единиц. Превышение даёт `RESOURCE_LIMIT`
   после просмотренного символа, без частичного значения. Пара не расходует бюджет частично.
6. Завершённый символ за объявленной границей тела даёт `INVALID_ENCODING` после проверки бюджета
   добавления. Этот приоритет бюджета — намеренная политика C++, а не измерение Java.

Примитив не обрезает вход по объявленному телу: `01c280` ошибочен на позиции 3, `01c2` неполон
на позиции 2, `014142` успешен на позиции 2 с одним оставшимся байтом. Чтение никогда не выходит
за переданный span. Нет обещания отката или возобновляемого состояния. Будущий frame parser обязан
передавать span, ограниченный кадром. Владеющий reader растёт только по просмотренным единицам
в пределах бюджета; `std::bad_alloc` или `std::length_error` могут распространяться, частичное
значение не возвращается. Поэтому reader намеренно не noexcept.

Preflight записи проверяет нижнюю границу wire-длины по числу входных единиц, затем их бюджет,
затем считает канонические байты с проверками переполнения через вычитание из 8589934588, затем
проверяет бюджет байтов тела и полную ёмкость span. Слишком большая длина даёт `INVALID_LENGTH`,
превышение политики — `RESOURCE_LIMIT`, непредставимый общий размер/недостаточная ёмкость —
`INSUFFICIENT_OUTPUT`. При любой ошибке written равен нулю и весь выход неизменен. При успехе
байты после `written` неизменны. Writer не выделяет память и является noexcept. Для проверки
арифметики не создаётся фиктивный огромный string_view: это нарушило бы предусловие доступной памяти.

Общий `Status` расширен исходами UTF; числовые значения прежних compact-статусов, гарантии noexcept,
отсутствие выделений памяти и результаты compact не изменены.

## Решение о повторном использовании, принятое до реализации

Хранение отделено от преобразования. Повторно используются C++23 `u16string`, `u16string_view`,
`optional`, `span`, арифметика фиксированной ширины и существующий compact codec. Контейнеры не
перекодируют. Устаревшие в C++23 `codecvt_utf8_utf16`/`wstring_convert` выполняют преобразование,
но не предоставляют нужные оболочку, ресурсы, атомарность выхода и Java-позиции. Они оценены по
[проекту C++23 N4950](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf)
и исполнены с GCC 13.3/libstdc++. Платформенное преобразование wchar_t не выбрано.

| Кандидат и официальный версионированный источник | Чтение | Запись | Стоимость и решение |
| --- | --- | --- | --- |
| [UTF-CPP 4.0.6](https://github.com/nemtrif/utfcpp/tree/v4.0.6), `source/utf8/checked.h`, `core.h`, `unchecked.h` | Проверяемый путь отвергает overlong и суррогаты; `validate_next` восстанавливает итератор при ошибке, в отличие от Java consumption. У unchecked `next` нет параметра конца: недоверенные усечённые данные требуют собственной проверки. | Проверяемое преобразование отвергает отдельные суррогаты. Unchecked-преобразование отбрасывает завершающий high surrogate и предполагает, что следующая единица завершает пару. | Header-only, для скопированных заголовков нужны уведомления BSL-1.0; нет runtime/транзитивной production-библиотеки. Итераторный API может не выделять память, строковые обёртки выделяют. Переносимый C++98+ и документированная поддержка MSVC; фактический probe только GCC. Адаптер границ/ошибок/оболочки и сегментация записи сохраняют собственную работу. Отклонён. |
| [simdutf 5.2.8](https://github.com/simdutf/simdutf/tree/v5.2.8), `include/simdutf/implementation.h`, README | Проверяемое преобразование отвергает измеренные нестандартные формы. API для корректного входа нельзя применять к ним и ошибочным префиксам. Позиция ошибки не равна Java consumed. | Проверяемое преобразование UTF-16 отвергает отдельные суррогаты. | MIT либо Apache-2.0; при выборе MIT нужны copyright/license notices. Компилируемая библиотека, CPU dispatch, дополнительные размер бинарного файла и затраты сборки; выход принадлежит вызывающему, обязательных production-зависимостей нет. Официально поддержаны GCC, LLVM Clang и Visual Studio; интеграция кандидата ClangCL не проверялась. Tests/tools отключены в фактическом GCC probe. Отклонён. |

Обе библиотеки могут преобразовать подмножество корректных скаляров в обоих направлениях. Это
не оправдывает второй путь: оболочка, preflight байтов/счётчиков, атомарная запись, инкрементальные
бюджеты и разбор нестандартного/ошибочного входа остаются собственными. Разбиение/исправление входа
ради переиспользования добавило бы сопровождение и проходы, не устранив критическую логику.
Unchecked-примитивы append UTF-CPP — лишь несколько сдвигов, не оправдывающих production-зависимость.
Поэтому реализован небольшой QD-специфичный codec; сторонний код реализации и типы не входят в API
и production-сборку. Нет заявлений о производительности и предположительных fast paths.

Исполненные решающие probes используют неизменные наблюдения `S-supplementary`, `S-high`, `S-low`,
`F-overlong2/3/4`, `F-cesu-pair`, `F-surrogate4`.
[Первоначальный probe библиотек](../../tests/conformance/encoding/utf-reuse-initial.log) предшествовал
реализации. [Итоговое точное сравнение](../../tests/conformance/encoding/utf-reuse.log) сравнивает байты
или единицы UTF-16 всех трёх кандидатов: совпадает только S-supplementary. В частности, отсутствие
исключения libstdc++ для завершающего high surrogate не означает успех: Java-байты не получены.
Этот ограниченный probe не является полной платформенной матрицей кандидатов.

## Воспроизведение probes кандидатов

[Генератор](../../tests/conformance/probe_utf_reuse.py) читает исходные TSV и проверяет SHA-256 архивов
перед созданием отдельного игнорируемого CMake-проекта. Основная сборка кандидатов не загружает.
Архивы релизов и извлечённые лицензии остаются в `.work/utf-reuse`; повторный запуск offline требует
этого кэша. Точная целостность архивов:

- UTF-CPP v4.0.6: `6920a6a5d6a04b9a89b2a89af7132f8acefd46e0c2a7b190350539e9213816c0`.
- simdutf v5.2.8: `2706f1bef85a6d8598f82defd3848f1c5100e2e065c5d416d993118b53ea8d77`.

Из WSL в корне репозитория (получение требует сети):

```bash
mkdir -p .work/utf-reuse
curl -L https://codeload.github.com/nemtrif/utfcpp/tar.gz/refs/tags/v4.0.6 -o .work/utf-reuse/utfcpp.tar.gz
curl -L https://codeload.github.com/simdutf/simdutf/tar.gz/refs/tags/v5.2.8 -o .work/utf-reuse/simdutf.tar.gz
python3 tests/conformance/probe_utf_reuse.py
tar -xf .work/utf-reuse/utfcpp.tar.gz -C .work/utf-reuse
tar -xf .work/utf-reuse/simdutf.tar.gz -C .work/utf-reuse
python3 tools/run_utc.py --log .work/utf-reuse/configure.log -- cmake -S .work/utf-reuse -B .work/utf-reuse/build -G Ninja -DCMAKE_BUILD_TYPE=Release
python3 tools/run_utc.py --log .work/utf-reuse/build.log -- cmake --build .work/utf-reuse/build -j 4
python3 tools/run_utc.py --log .work/utf-reuse/probe.log -- .work/utf-reuse/build/probe
```

## Ограничения проверки

[Покрытие](../../tests/conformance/encoding/COVERAGE.ru.md) и
[валидация](../../tests/conformance/encoding/VALIDATION.ru.md) перечисляют исполненные конфигурации,
негативные проверки и неизменные свидетельства. Не охвачены огромные допустимые выделения памяти,
инъекция отказов аллокатора, 32-битное исполнение, другие реализации BufferedInput, другие Unicode API,
полный Unicode/QTP, PentaCodec, importer и transport. API остаётся предварительным.
