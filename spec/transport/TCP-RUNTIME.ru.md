# TCP runtime под управлением вызывающей стороны

[English version](TCP-RUNTIME.md). Английская версия нормативная.

Явно включаемые проверки активности, конечное число переподключений и повторная
отправка желаемых подписок описаны в отдельном [контракте восстановления соединения](RECOVERY.ru.md).

`qd/transport/tcp_runtime.hpp` — опциональный TCP-адаптер без учётных данных для
[чистой live-сессии](../subscriptions/LIVE-SESSION.ru.md). Он владеет одним запуском
и одной эпохой протокола. TLS, прикладные callbacks, коллекторы, переподключение
и фасад клиента подписок здесь не реализуются.

## Владение и продвижение

Создавайте `RuntimeBootstrap` на главном потоке приложения до остальных прикладных
потоков. Согласуйте SDK reference со всеми другими пользователями c-ares. Сохраняйте
объект до завершения всех runtime и прикладных потоков, затем уничтожайте на том же
потоке. Runtime не выполняет глобальную очистку c-ares. Нарушение предусловия
времени жизни/потока borrowed bootstrap приводит к terminate вместо очистки SDK
под активным пользователем.

До SDK ownership bootstrap один раз обращается к native entropy: Windows сообщает
отказ `RtlGenRandom` как типизированный bootstrap failure без SDK cleanup.
У Linux `arc4random_buf` нет recoverable status; нормальный возврат не обещает
будущую доступность. Native failure/latency остаётся явным предусловием платформы,
как уточняется в [ADR-0006](../../docs/decisions/ADR-0006-live-runtime.ru.md).

`TcpRuntime::create` проверяет и копирует заимствованные настройки endpoint/серверов,
затем принимает схему и компоновщик после потенциально ошибочной подготовки.
При отказе исходные объекты сохраняются. Числовые IPv4/IPv6 обходят DNS. Имена
задаются явно как ASCII/A-label: URI, service-name, IDNA, окружение, hosts-файл
и системный resolver не используются. Исходное имя хранится отдельно от адресов
для последующей проверки TLS identity.

`socketSendBufferBytes` задаёт запрос `SO_SNDBUF` для собственного сокета; ноль
сохраняет нативное значение по умолчанию. Положительное значение должно помещаться
в нативный integer option. ОС может изменить запрос, в том числе округлить
или удвоить его. Kernel socket buffers не включаются этим в учёт SDK storage.

`start` активирует запуск. `poll` выполняет ограниченное продвижение и возвращает
не более одного целиком принятого владеющего `LiveEvent`. Непринятые сессией байты
остаются в собственном read suffix до следующего чтения сокета. Событие и снимок
удерживают неизменяемую память протокола после последующей ошибки или уничтожения
runtime.

Все операции, перемещения, запросы, уничтожение runtime и освобождение связанных
protocol owners сериализованы и невложены на создающем потоке. Действия с результатом
`expected` отклоняют другой поток; для queries/перемещения/уничтожения принадлежность
потоку — предусловие. Это не межпоточный command port.

Asio timer service/helper не создаются. Вызывающая сторона продвигает монотонные
сроки и DNS ticks вызовами poll; `nextWake` — подсказка планировщику. Host отдельно
обеспечивает частое продвижение pending I/O: подсказка не является уведомлением
готовности сокета и не разрешает игнорировать её до далёкого deadline. Linux использует
готовность и одну нативную попытку receive/send. EINTR/EAGAIN не запускает бесконечный
цикл повторов в том же такте. Windows использует прямой IOCP для подключённых данных
и ограниченную проверку нативного nonblocking connect, исключая скрытый поток
select-reactor SDK.

## Вывод и завершение

Методы протокола, heartbeat, описаний и подписок компонуют сообщение в один владеющий
output slot. Занятый slot отклоняет новый вывод до компоновки. API не принимает
произвольные wire bytes и не передаёт authorization через plain-адаптер. Локальная
компоновка и принятие сокетом отделены от подтверждения другой стороны.

`requestClose` — идемпотентный запрос abort, а не завершение. Он прекращает приём
и новый вывод, уничтожает DNS channel вне callbacks, отменяет/закрывает работу сокета.
Продолжайте poll до `CLOSED` и появления terminal evidence. Завершение означает,
что все собственные handlers вернулись; поздний внутренний callback не обращается
к освобождённому состоянию. Успешный результат записи в гонке учитывается один раз.
Terminal evidence разделяет первичную ошибку, отдельную вторичную ошибку, сообщённые байты записи,
известный отброшенный входной суффикс и локальный pending output suffix. Успешные
native-send counts Linux показывают локальное принятие. Отменённая или ошибочная
Windows overlapped write может оставить принятие неизвестным; terminal flag сохраняет
эту неопределённость. Pending output может включать незачтённый принятый префикс:
его нельзя называть точно неотправленным или автоматически повторять.

Peer EOF явно завершает вход протокола; неполный кадр — ошибка протокола.
Прежние принятые владельцы остаются действительными. Уничтожение без close
использует fallback внешнего завершения host, включая drain completions. Этот
fallback не является API наблюдаемого ограниченного retirement или гарантией
жёсткого срока исполнения.

## Профиль DNS

Используйте [квалифицированные receipts исходников](../../cmake/runtime-profile/README.ru.md),
аллокаторы c-ares по умолчанию и явные 1–4 числовых IPv4 DNS-сервера. Разрешайте A,
затем AAAA, по одному wire query, без следующего запроса внутри C callback.
Cache/search/aliases/sorting/EDNS и failed-server probes отключены. UDP-to-TCP
fallback остаётся внутри ограниченного профиля. Для retirement уничтожайте канал:
один `ares_cancel` может оставить активные запросы при отказе выделения памяти.

Адреса для connect поступают только от запрошенного owner name или его ограниченной
проверенной на цикл цепочки CNAME в этом ответе. Посторонние записи игнорируются.
Relevant escaped/non-A-label presentation names не поддерживаются. Ответ только
с CNAME не вызывает скрытых follow-up queries. Обе семьи собираются в конечный
массив без дубликатов до последовательных попыток connect; переполнение отклоняет
результат, без молчаливого усечения адресов.

## Границы ресурсов и работы

Фиксированные ёмкости адаптера/input/context/handlers и резерв эпохи протокола
учитываются всё время жизни. DNS имеет отдельный консервативный бюджет retained/
candidate/temporary SDK storage по исходникам, включая ёмкость контейнеров
и moving realloc. Это резервирование запрошенной памяти, без allocator overhead,
kernel buffers, RSS процесса и измеренной задержки. Независимые копии вызывающей
стороны остаются вне дерева владения запуска.

`TcpWork` и `LiveWork` — бюджеты выбранного вызывающей стороной такта; они
не сбрасываются автоматически и не возвращаются. Запросы socket buffers списываются
до submission, в том числе для частичных/отменённых операций. Попытки DNS callbacks
делят квоты между дескрипторами; исчерпание возвращает WOULD_BLOCK до новой нативной
попытки. Полные UDP datagrams сохраняются. До SDK progress entry нужен консервативный
бюджет parser/copy/lifecycle работы; deadline не прерывает разбор. Control retirement
имеет отдельный конечный бюджет и не зависит от обычных data credits. Доступность
нативных OS/entropy services — явное предусловие платформы, а не hard real-time promise.

## Граница сборки

`ORG_TTLDTOR_QDCXX_BUILD_RUNTIME` по умолчанию OFF. Включение требует явных
квалифицированных корней Asio/c-ares; хеши исходников SDK проверяются до компиляции.
Публичные заголовки используют стандартные/проектные типы. Установленный статический
target сохраняет native link closure и notices зависимостей. При runtime OFF SDK
не ищутся/не скачиваются; зависимости JSON, recording, replay и чистых библиотек
не меняются.

[Нативная матрица](../../tests/conformance/transport/TCP-VALIDATION.ru.md) задаёт
профили исполнения и границы доказательств retained owners/pending operations.

## Отдельный интерфейс проверенного TLS

Реализованный [TLS runtime](TLS-RUNTIME.ru.md) сочетает общего владельца native-операций/DNS
с отдельным ограниченным движком memory BIO и [контрактом ресурсов/работы](TLS-RESOURCES.ru.md).
Этот обычный `TcpRuntime` остаётся без поставщика учётных данных и не получает TLS-поведение
из сохранённых параметров endpoint. Выделение общего ядра обязано сохранить прежнюю семантику TCP
и пройти полную регрессию. Проверки заголовка/ресурса TLS её не заменяют и не подтверждают
завершённую квалификацию реализации TLS;
см. [текущие доказательства](../../tests/conformance/transport/TLS-VALIDATION.ru.md).

### Текущая граница доказательств TLS

Рабочий TLS runtime реализован. Целевой набор текущих исходников прошёл 39 native-тестов: Windows MSVC 19.42 x64 Release /MD — 11 486 проверок; Linux GCC 13.3 x64 Debug ASan+UBSan — 11 625 проверок, LSan выключен. Полная регрессия на каждой ОС прошла 58/58 тестов с JSON и 57/57 без JSON. Проверка сгенерированной справки учитывается отдельно. Обновлённый установленный пакет прошёл четыре TLS 1.2/1.3 запуска на двух ОС. Результаты отдельных проверок не означают выпуск, полную поддержку подписок или сертификацию безопасности. Актуальный перечень выполненных и только обоснованных исходниками случаев находится на странице квалификации TLS, ссылка на которую приведена выше.

Приватная протокольно-независимая байтовая операция описана отдельно в [BYTE-OWNER](BYTE-OWNER.ru.md).
