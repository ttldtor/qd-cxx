# Проверка составного профиля Beast WSS

[English version](BEAST-WSS-VALIDATION.md). Английская версия нормативная.

Проверка охватывает [внутреннюю сессию источника WSS](BEAST-WSS-SESSION.ru.md) на Boost
1.92.0 и квалифицированном статическом SDK OpenSSL 3.5.9. Сессия и синтетические серверы
соединяются по loopback. Для проверки пакета используется отдельный потребитель зависимости.

## Профили проверок

| Проверка | Windows x64 | Linux x86-64 |
| --- | --- | --- |
| Внутренняя сборка WSS и CTest | 5 из 5 групп, MSVC 19.42 Release с динамическим CRT | 5 из 5 групп, GCC 13.3 Debug с ASan/UBSan |
| Потребитель из перемещённого SDK | Собрался, слинковался и запустился | Собрался, слинковался и запустился с ASan/UBSan |
| CTest для TCP, контролируемого TLS и recovery | 23 из 23 групп, тот же профиль Windows со standalone Asio | 23 из 23 групп, тот же профиль Linux со standalone Asio |

Пять групп WSS проверяют подготовку зависимостей, TLS, наблюдение за аллокациями TLS, upgrade
и ограниченную доставку сообщений. Независимый loopback-сервер участвует в проверках предела
сообщения, фрагментации UTF-8, pong, обоих направлений закрытия, обрыва транспорта, ошибочных
кадров, отмены и дедлайнов чтения, записи и закрытия.

Составной стенд открывает восемь новых попыток в одном прогретом процессе. Каждая начинается
после уничтожения предыдущего владельца и его сервера. Стенд чередует отмену ожидающего
чтения с отменой записи, заблокированной сервером, который не читает данные. Новые сессии
получают собственный текст, а сохранённое значение первой сессии остаётся читаемым после
последнего закрытия. После восьми попыток счётчик дескрипторов Windows сохранил значение 144,
а число открытых файловых дескрипторов Linux осталось 7, включая дескриптор перечисления.
При отсутствии якорей доверия попытка отклоняется до работы с сетью. При явном доверии и
привязанном порте без слушателя попытка возвращает отказ в подключении без перехода в `READY`.

Отдельная конфигурация QTP охватывает TCP, контролируемый TLS, необработанные байты, владение
сокетом и резолвером, восстановление и его нативный стенд, а также остановку подписок.
Цель QTP использует standalone Asio. Установленная зависимость WSS использует Boost.Asio.

При выключенном параметре отдельная конфигурация WSS пропускает поиск компилятора и SDK
даже с отсутствующими входными путями. Включённый профиль требует явный путь к подготовленному
Boost. Перемещённый SDK предоставляет внутреннюю цель зависимости `qdcxx_private::beast_wss`
и проверяет переданный SDK OpenSSL. Установленный потребитель создаёт три транспортных слоя
и успешно завершается без подключения.

## Повторение проверок

Настройте `build-wss` по [инструкции подготовки и сборки](../../tools/deps/BEAST-WSS.ru.md).
В Windows нужна консоль квалифицированного MSVC Release с `/MD`. Для GCC 13.3 Debug в Linux
примените параметры и настройки тестирования ниже как к WSS, так и к сборке транспорта со
standalone Asio. Для C-компилятора транспортной сборки также выберите `gcc-13`.

```bash
export ASAN_OPTIONS=detect_leaks=0:halt_on_error=1
export UBSAN_OPTIONS=halt_on_error=1
# Add these arguments to each Linux CMake configure command.
# -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=g++-13
# '-DCMAKE_CXX_FLAGS=-fsanitize=address,undefined -fno-omit-frame-pointer -fno-pie'
# '-DCMAKE_EXE_LINKER_FLAGS=-fsanitize=address,undefined -no-pie'
```

```text
cmake --build build-wss --parallel 2
ctest --test-dir build-wss --no-tests=error --output-on-failure
cmake --install build-wss --prefix wss-sdk-staging
```

Переместите `wss-sdk-staging` в новый каталог и настройте
[отдельный потребитель](../../tests/conformance/beast-wss-dependency/consumer/CMakeLists.txt).
Передайте абсолютный `SDK_ROOT` после перемещения, те же параметры компиляции и явный
квалифицированный `ORG_TTLDTOR_QDCXX_OPENSSL_ROOT`. Соберите и запустите
`qdcxx_beast_wss_consumer` из каталога сборки потребителя. Код 0 подтверждает проверку зависимости.

Для регрессий корневого проекта примените параметры
[контролируемого TLS](../../docs/CPP-BUILD.ru.md#tls-source-profile-cpp-build-ru).
В дополнение к клиенту, runtime и TLS задайте `BUILD_TESTING=ON` и
`ORG_TTLDTOR_QDCXX_BUILD_RECOVERY=ON`. Установите `ORG_TTLDTOR_QDCXX_BUILD_SCHEMA_JSON=OFF`
и `ORG_TTLDTOR_QDCXX_BUILD_EXAMPLES=OFF`. Для офлайн-сборки задайте путь к закреплённым
исходникам doctest через `FETCHCONTENT_SOURCE_DIR_DOCTEST`. Используйте отдельный каталог
корневой сборки на каждой платформе. После сборки запустите выбранные группы CTest.

```text
cmake --build build-transport --parallel 3
ctest --test-dir build-transport --no-tests=error --output-on-failure -R "^(transport_(bootstrap_lease|raw_bytes|tcp|cares_ownership|tls|recovery).*|subscription_shutdown)$"
```

## Границы проверки

В Linux компиляция C++ и линковка программ используют ASan/UBSan с отключённым LeakSanitizer. OpenSSL
поступает из закреплённого предварительно собранного статического SDK. Счётчики дескрипторов
относятся к этой конечной loopback-нагрузке. [Наблюдение аллокаций TLS](BEAST-WSS-TLS.ru.md)
учитывает запрошенные байты OpenSSL на собственном стенде. Пиковый RSS, общий TLS хоста,
поведение при отказе аллокатора и жёсткий предел времени нативного DNS-вызова вне этой проверки.
Устанавливается внутренний пакет зависимости. Восстановление подписки провайдера, доступ к
живой площадке и пакет шлюза требуют отдельных проверок.
