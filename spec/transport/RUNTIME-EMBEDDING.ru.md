# Встраивание runtime и владение bootstrap {#runtime-embedding-ru}

[English](RUNTIME-EMBEDDING.md) · [TCP runtime](TCP-RUNTIME.ru.md) · [Feed API](../../docs/FEED-API.ru.md)

Это решение о владении bootstrap для будущего API встраивания. Текущий конструктор
`ApiRuntime` по-прежнему получает собственный bootstrap и требует создания на
главном потоке до остальных потоков приложения. Описанное ниже заимствование
инициализации этим решением не реализовано. Здесь не добавлены конструкторы,
перегрузки, проверки runtime или поддержка двоичной интеграции и плагинов.

## Действующие требования

Квалифицированный профиль — Windows x64/MSVC либо Linux x86-64/GCC со статическим
[c-ares 1.34.9+qdcxx2 и `CARES_THREADS=OFF`](../../cmake/runtime-profile/README.ru.md).
Используйте аллокаторы c-ares по умолчанию. Создавайте `RuntimeBootstrap` на главном
потоке приложения до остальных потоков, согласуйте всех других пользователей того
же состояния SDK и сохраняйте владельца до завершения всех runtime и потоков
приложения. Уничтожайте его на создавшем потоке, вне Windows `DllMain`.

Каждый успешно созданный владеющий bootstrap получает собственный сбалансированный
SDK reference; на Windows перед инициализацией c-ares также получается Winsock
reference. Заёмщики runtime удерживают стабильное состояние bootstrap и никогда
не выполняют глобальную очистку SDK. Уничтожение при живых заёмщиках или на другом
потоке завершает процесс. Само закрытие endpoint не освобождает bootstrap процесса.

Текущий feed runtime владеет этим bootstrap, лениво запускает worker и присоединяет
его до уничтожения bootstrap. Дескрипторы endpoint/subscription могут оставаться
закрытыми отсоединёнными портами после освобождения native-состояния. Это не
разрешает им продолжать DNS, работу с сокетами или callback к уже освобождённому
состоянию runtime. См. [владение и завершение TCP](TCP-RUNTIME.ru.md#владение-и-продвижение)
и [правила времени жизни feed](../../docs/FEED-API.ru.md).

## Выбранные будущие режимы владения

Оба режима сохраняют действующий профиль ресурсов native/DNS и обязанности
вызывающей стороны. Имена элементов API и отображение ошибок определяются при реализации.

| Режим | Владение SDK | Поддерживаемый порядок создания |
| --- | --- | --- |
| Владеющий | Feed runtime получает и затем освобождает собственный bootstrap reference, сохраняя действующий путь. | Создание на главном потоке до остальных потоков приложения; уничтожение там же после их завершения. |
| Заимствующий | Feed runtime удерживает явное заимствование существующего живого `RuntimeBootstrap`; не выполняет глобальную инициализацию, очистку или смену аллокаторов. | Bootstrap создаётся на главном потоке до остальных потоков приложения; feed runtime создаётся и уничтожается позже на том же главном/создавшем потоке. |

Заимствующий режим поддерживает уже многопоточный хост, только если тот подготовил
контролируемый bootstrap до запуска потоков. Он принимает живой токен QDCXX
bootstrap, а не логическое утверждение, что другая библиотека инициализировала
c-ares. Токен задаёт контролируемую связь времени жизни; он не доказывает, что все
внешние пользователи соблюли требования к аллокаторам, порядку и координации.

Реализация должна проверить поддерживаемое происхождение токена и отклонить
несовместимый экземпляр до активации native-работы. Совпадающий тип C++, строка
версии или имя общей библиотеки не подтверждают совместимость между DSO, образами
SDK или плагинами. Двоичные/плагинные интеграции без явно поддерживаемого контракта
происхождения остаются неподдерживаемыми. Новый ABI или механизм обнаружения
образов SDK здесь не выбран.

## Время жизни заимствования и границы ошибок

1. Хост создаёт bootstrap на главном потоке до запуска остальных потоков и
   сохраняет владение SDK references. Всех внешних пользователей того же состояния
   c-ares нужно согласовать; никто не должен менять аллокаторы или преждевременно
   выполнять cleanup.
2. Будущий заимствующий конструктор проверяет конфигурацию, живой токен/происхождение
   и общий главный/создавший поток до публикации пригодного runtime или активации
   native-работы. Перемещённый либо иной несовместимый токен вызывает отказ без
   получения или освобождения глобального SDK reference. При ошибке временное
   заимствование освобождается, а владелец хоста сохраняется.
3. После успешного создания заимствование стабильного состояния сохраняется в
   периодах бездействия, при ожидающих endpoint, запуске worker, ошибке и асинхронном
   завершении. Перемещение оболочки владельца не должно инвалидировать состояние
   или ослаблять предусловия потока и времени жизни. Создание заёмщика не продвигает SDK.
4. Завершение runtime запрещает новый приём работы, освобождает native-состояние
   DNS/сокетов и ждёт завершения worker и принадлежащих callback/captures. Только
   после этого можно освободить заимствование. Запрос закрытия, отмены или терминальное
   уведомление endpoint сами по себе недостаточны для подтверждения полного завершения.
5. Хост уничтожает bootstrap на исходном главном потоке после завершения всех
   заёмщиков и потоков приложения. Сохраняются действующие защиты от уничтожения
   при живом заимствовании и на неверном потоке. Ни endpoint, ни callback, ни
   отсоединённый дескриптор не выполняют глобальную очистку от имени хоста.

Вызовы с другого потока и неверный токен/состояние должны отклоняться через публичный
механизм ошибок там, где операция может сообщить об отказе, до native-активации.
Для уничтожения без результата сохраняются действующие fail-fast предусловия
времени жизни. Реализация обязана сохранить эти проверки runtime; решение не
доказывает, что текущий API уже выполняет их все. Нельзя надёжно восстановить,
инициализировал ли хост SDK до посторонних потоков и соблюдал ли каждый внешний
пользователь SDK свои обязанности.

## Почему проверки инициализации недостаточно

Закреплённый `src/lib/ares_library_init.c` использует неатомарный глобальный unsigned
счётчик ссылок. `ares_library_init` увеличивает его; `ares_library_cleanup` уменьшает
и сбрасывает глобальные allocator hooks при нуле. `ares_library_init_mem` меняет
эти hooks перед вызовом `ares_library_init`, даже при уже существующей инициализации.
Локальный mutex только для вызовов QDCXX не координирует внешних пользователей SDK.

На Windows `ares_library_initialized()` проверяет лишь ненулевой счётчик. На Linux
проверка `USE_WINSOCK` отсутствует, и функция возвращает успех даже при нулевом
счётчике. Ни один результат не подтверждает идентичность аллокаторов, баланс владения,
инициализацию до потоков или отсутствие параллельных внешних вызовов.
`ares_threadsafety()` и проверки версии не дают этих сведений. Перечисление потоков
не восстанавливает эту историю и не предотвращает последующую гонку.

Закреплённые руководства init/cleanup сохраняют требования до/после остальных
потоков и запрет вызовов из Windows `DllMain`. Малый объём квалифицированной
реализации init не ослабляет поддерживаемый контракт.
[Манифест исходников профиля](../../cmake/runtime-profile/c-ares-1.34.9-qdcxx2.sources.json)
связывает `src/lib/ares_library_init.c` с SHA-256
`d4baba72385dc656ff9afc4015d7fbc67805194f563e4995ac9d3a04ffbee90c`
и включает `docs/ares_library_init.3` и `docs/ares_library_cleanup.3`.
Страницы upstream описывают [инициализацию](https://c-ares.org/docs/ares_library_init.html)
и [очистку](https://c-ares.org/docs/ares_library_cleanup.html); для квалифицированного
профиля определяющими являются закреплённые исходники и руководства. Сохраняется
требование к уведомлению MIT SDK и действующим сведениям об исходниках/лицензиях профиля.

## Неподдерживаемые условия хоста и проверки реализации

Поздний bootstrap с нуля в многопоточном хосте, raw-флаги внешней инициализации,
принятие по одной проверке состояния, несогласованное использование того же
SDK-состояния и активация из `DllMain` не поддерживаются. Статическая компоновка
или вторая DLL сами по себе не доказывают изоляцию SDK-состояния. Отдельный процесс
возможен как решение приложения со своими затратами на IPC, ресурсы и завершение;
это решение не реализует и не квалифицирует средство изоляции.

Реализация обязана проверить как минимум: совместимость владеющего startup;
bootstrap хоста на главном потоке, затем потоки хоста и более поздний заимствующий
runtime; нескольких заёмщиков и периоды бездействия; ошибку создания без cleanup
хоста; неверный/перемещённый токен и отказ с другого потока до активации; завершение
с ожидающими DNS/сокетами и закрытием/исключением из callback; освобождение только
после полного покоя; fail-fast уничтожение владельца при живом заёмщике. Для
поддерживаемого происхождения токена нужны положительные проверки и проверки отказа.
При реализации обязательны native-проверки на квалифицированных Windows и Linux.
Это будущие приёмочные сценарии, а не результаты выполненных тестов.

Решение о владении не меняет протокол, TLS, credentials, глобальные настройки,
зависимости SDK, ресурсные границы runtime или действующие утверждения о проверках
исходников. [Контролируемый TLS-профиль](TLS-RUNTIME.ru.md) сохраняет отдельный контракт.
