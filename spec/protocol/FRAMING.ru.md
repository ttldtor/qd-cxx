# Ограниченное инкрементальное выделение кадров QTP

[English version](FRAMING.md). Английская версия является нормативной.

QDCXX-012 разделяет выделение кадров, обработку payload и политику закрытия соединения.
Предварительный компонент `qdcxx_protocol` зависит от `qdcxx_encoding`; обратной зависимости нет.
Transport, декодирование payload, frame writer, сборка PART и механизмы сессии не включены.

## Доказательства и wire-контракт

Oracle — Java QD 3.355 / `0ddc0a09779fb61d74cc0b37c6449ff47dcb715f`.
[Покрытие и provenance P02](../../tests/fixtures/protocol/p02/COVERAGE.ru.md) фиксируют исполненные
наблюдения `BinaryQTPParser`. [Источники](SOURCES.md) указывают parseImpl, parseMessageType,
parseHeartbeat, диагностический appendBytes и обработчики ошибок MessageAdapter.

Кадр — `compact-long(length) | body`. Неотрицательная длина считает только байты body. Нулевой
body означает EMPTY_HEARTBEAT без type; ненулевой начинается с compact-long(type) в диапазоне
0..2147483647, затем следует непрозрачный payload. Избыточные compact-представления принимаются.
Оба поля используют readCompactLong. Span type ограничен концом body. Неполный внешний prefix/body
ожидает ввод, сохраняя все байты; неполный type в полном body даёт TRUNCATED_TYPE. Отрицательная
длина даёт INVALID_LENGTH; отрицательный/слишком большой type — INVALID_TYPE.

В P02 `empty` и `explicit-zero` продвигают ввод Java без heartbeat callback. Hooks — наблюдательная
инструментация, а не выдуманные callbacks. `tiny-heartbeat` даёт один callback. Неизвестный type 62
структурно допустим: возвращающийся consumer Java сообщает unknown, затем обрабатывает heartbeat.
Повреждённый payload heartbeat вызывает message corruption в Java, но остаётся допустимым
непрозрачным кадром C++. Стандартный MessageAdapter закрывается при измеренном unknown message;
эта политика не относится к выделению кадров. Восстановление Java после ошибки body при возврате
consumer не является политикой жизненного цикла C++.

Диагностика Java при ошибке длины читает дополнительные доступные байты (appendBytes), поэтому
позиция и обработка следующего кадра после неверной длины могут зависеть от разбиения feed.
Счётчик принятых байтов C++ намеренно останавливается на неверном prefix либо на полном body при
ошибке type. Списки callbacks/позиции Java не являются ожиданиями кадров C++. Проекции кадров
сохраняют provenance входа и явно применяют политику первой ошибки.

## Предварительный API, владение и обратное давление

[frame_reader.hpp](../../include/qd/protocol/frame_reader.hpp) определяет FrameReader, FrameLimits,
Frame, FeedResult, FrameStatus и FrameError. Использование однопоточное и нереентерабельное.
`feed(span<const byte>)` заимствует ввод только на время вызова и возвращает не более одного
владеющего кадра. `accepted` считает скопированные байты этого вызова, включая неполные и
ошибочные байты, без непринятого суффикса. Повторно передавайте суффикс до его исчерпания или ошибки;
пустой feed не означает EOF. Выдача одного кадра обеспечивает обратное давление: внутренней
очереди выхода нет, объём выделения памяти не зависит от размера большого feed.
`totalAccepted()` считает байты после reset. `pending()` показывает точные сохранённые байты,
включая prefix длины; view истекает при следующей изменяющей операции или уничтожении. Ввод не
должен ссылаться на этот внутренний view.

Frame различает EMPTY_HEARTBEAT и MESSAGE, содержит optional type, владеющий payload и начальное/
конечное смещения потока. Владение сохраняется после feed, reset и уничтожения reader.
Callbacks не используются. FRAME_READY содержит кадр, остальные результаты — нет.
NEED_INPUT включает чистую границу. `errorOffset()` — начало ошибочного кадра; при OFFSET_OVERFLOW
это начало текущего неполного кадра. Значение интерпретируется только при FAILED.

## Ограничения и жизненный цикл

Оба конечных бюджета обязательны: maximumBodyBytes и maximumPendingBytes. Конфигурация отклоняется,
если body превышает знаковый 64-битный диапазон, body+9 переполняет size_t либо pending меньше
body+9. Нулевой бюджет body допустим и разрешает пустые heartbeat. Девять — максимальный размер
compact-long prefix. Знак длины проверяется до преобразования и выделения body. Превышение бюджета
длины даёт BODY_LIMIT сразу после prefix.

Reader один раз при создании выделяет ровно bodyBudget+9 элементов byte независимо от большего
pending-бюджета; служебные данные allocator учитываются дополнительно. Pending не превышает этот
буфер. Выданный payload отдельно владеет не более bodyBudget-1 байтами (ноль при bodyBudget=0).
Реализация запрашивает одно выделение payload при выдаче; накладные расходы allocator/container
не входят в побайтовую гарантию heap. Сохранённые вызывающей стороной кадры принадлежат ей, их
суммарная память reader не ограничивается. Недоверенная длина не вызывает предварительное
выделение body. Суммарный uint64 offset проверяется до принятия байтов; переполнение терминально.

Первая framing/resource-ошибка терминальна: ошибочные pending-байты сохраняются, ранее выданные
кадры остаются действительными, следующие feed принимают ноль. Сканирования и автоматической
ресинхронизации нет. Ошибка выделения в конструкторе выбрасывает исключение; bad_alloc/length_error
при выдаче превращается в терминальную ALLOCATION_FAILURE с точным accepted и сохранёнными
байтами. Ошибка выделения не является wire-классификацией. Пользовательских callbacks в feed нет.

`finish()` явно завершает ввод: чистая граница даёт FINISHED, pending — TRUNCATED_INPUT,
предыдущая ошибка остаётся FAILED. Следующие feed принимают ноль; повторный finish идемпотентен.
Это политика C++: в базовом Java parse нет final-EOF метода. `reset()` очищает только байты,
счётчики и жизненный цикл framer, сохраняет выделенный буфер и не имеет семантики Java resetSession.
Выданные кадры остаются действительными.

## Область conformance

[Валидация протокола](../../tests/conformance/protocol/VALIDATION.ru.md) фиксирует P01 и все 17
входов P02: целиком/каждое разбиение на две части/побайтно/пустые и выбранные многочастные подачи,
независимые проекции кадров, точные pending-байты, проверки ресурсов/обратного давления/владения
и отрицательную проверку fixtures. Синтаксис payload, комбинации политик adapter, огромные
выделения, инъекция allocation failure, исчерпание offset и другие архитектуры не проверены.
