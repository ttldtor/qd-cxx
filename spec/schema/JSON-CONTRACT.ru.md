# Контракт JSON разрешённой локальной схемы — версия 1

[English version](JSON-CONTRACT.md). Английский документ является основным.

QDCXX-008, 2026-09-21. Это спроектированный контракт обмена, реализующий принятый [ADR-0001](../../docs/decisions/ADR-0001-normalized-model-boundaries.ru.md), включая уточнения утверждённого решения. Это не JSON, произведённый Java. [Покрытие](examples/COVERAGE.ru.md) сопоставляет все 17 существующих подслучаев; [валидация](examples/VALIDATION.ru.md) отделяет проверки документов от соответствия реализации.

## Граница и политика версий

Один документ JSON представляет либо успешно разрешённую локальную схему, либо отказ разрешения. Три границы владения не требуют трёх форматов. Core читает успешные `records` непосредственно, без открытия provenance, XML или истории построения. Здесь не определяются importer, хранение/API C++, библиотека JSON, канонические байты/хеш или сохранение всей сессии.

`formatVersion` — целое `1`; `profile` — ровно `{"id":"qd-3.355-xml-captured","version":1}`. Версии формата описывают представление; версии профиля — поведение. Неподдерживаемые версии формата/профиля и идентификаторы отклоняются до интерпретации записей; скрытая миграция запрещена. Профиль ограничен 17 подслучаями, закреплённым QD 3.355 commit `0ddc0a09779fb61d74cc0b37c6449ff47dcb715f`, прямой загрузкой XML, отключёнными sysprops/dxprops и доказательствами provider/environment по ссылкам. Поддержка произвольного XML не заявляется. Программное построение требует последующего профиля; поведение copied-main-alias относится только к этому профилю XML-импорта.

Неизвестные поля отклоняются на каждом определённом уровне объектов. Только необязательный корневой объект `extensions` допускает произвольные ключи с пространством имён и значения JSON, содержащие лишь данные: читатели могут игнорировать их и никогда не должны менять семантику на их основании. Расширения не могут вводить обязательное поведение. Повторяющиеся ключи объекта, числа вне JSON, некорректный Unicode и непарные суррогаты недопустимы. Используется UTF-8; порядок полей объекта и пробелы незначимы. Массивы сохраняют порядок; запрещено менять регистр, обрезать пробелы, удалять точки или нормализовать Unicode в именах.

Все поля ниже обязательны, если явно не указано иное. `null` разрешён только для `fieldId` слота, `fieldId` индекса и диагностического `serialTypeId` со значениями ниже. Отсутствие обязательного поля — ошибка, а не значение по умолчанию. Пустые массивы означают известную пустую коллекцию; `records:[]` — успешный пустой XML, а не отказ или неизвестная схема. Пустые имена/ссылки недопустимы. В этой версии нет числовых значений данных, временных меток, дробных чисел или 64-битных значений payload. ID/ordinal — целые числа JSON в диапазоне 0..2147483647 (boolean не является целым); версии — положительные целые того же диапазона. Полные serial type ID находятся в этом диапазоне, но профиль допускает только таблицу ниже. Для больших будущих значений требуется отдельно определённое представление.

## Корень и provenance

| Поле | Значение |
| --- | --- |
| `formatVersion`, `profile` | Версии и профиль выше; у profile только обязательные `id` и `version`. |
| `kind` | `local-schema` или `resolution-failure`; определяет обязательное тело. |
| `provenance` | Объект с `inputs`, `profileEvidence`, `expectationRef`. |
| `records` | Обязателен только для `local-schema`; упорядоченные выданные записи. Запрещён при отказе. |
| `diagnostics` | Обязателен только для `resolution-failure`; непустой массив диагностик в порядке зафиксированных попыток. Запрещён при успехе. |
| `extensions` | Необязательный непрозрачный объект, описанный выше. |

`provenance.inputs` — упорядоченный массив объектов `{ref, sha256}`, по одному на каждое вхождение корневого входа, включая повторения. `ref` — непрозрачная непустая ссылка на ресурс; в примерах это относительный путь от файла JSON. `sha256` — 64 шестнадцатеричных символа нижнего регистра, идентифицирующие исходные байты входа, а не канонический хеш схемы. Пустые inputs означают отсутствие переданных URL. `profileEvidence` — упорядоченный массив ровно из двух ссылок: сначала метаданные capture (upstream, команды, loader/provider/classpath fingerprints), затем inventory окружения (порядок providers и свойства). `expectationRef` идентифицирует неизменный TSV, по которому спроектирована проекция. Эти ссылки обязательны для прослеживаемости, но не являются инструкциями что-либо загружать или исполнять; недоступность доказательств не мешает core использовать схему. Аудит доказательств может отдельно сообщать о недоступных ресурсах.

Исходные входы и их порядок сохраняют disabled entities, templates, docs, aliases, включая объявления explicit-main, enums, tags, bitfields и custom type declarations без включения XML AST или движка операций. Ссылки не обещают исполнения этих возможностей. В S08-main-alias сохранённые исходник/TSV явно отмечают Chosen.Name как main для обеих записей, тогда как разрешённая Copy использует First.Name. Потребители обязаны использовать разрешённые effective names, а не вычислять их заново из provenance. Подробные origins полей/трассы операций отложены; исходные входы и expectation сохраняют зафиксированную информацию. Доказательства профиля включают наблюдаемые null default mappings/пустые mapping lists для этих искусственных имён; исполняемые Java mapping classes не сериализуются.

## Записи, поля и Java projection

Каждая запись — `{id, name, hasTime, fields, indexes, javaSlots, lookups}`. `id` равен позиции в `records`, локален для артефакта и не означает sender ID. `name` записи — точная непустая строка, уникальная в артефакте; поиск записи выполняется по точному имени. `hasTime` — boolean. Массивы `fields` и `indexes`, объект `javaSlots` и массив `lookups` присутствуют всегда.

Каждое поле — `{id, semanticName, effectiveName, fullName, localName, propertyName, serialTypeId}`. `id` равен позиции в `fields` записи; ссылки локальны для записи. Поля — активные логические значения в порядке объявлений разрешённой модели до разбиения Java по категориям и переноса индексов; disabled fields и синтетические позиции VOID исключены. `semanticName` — исходное имя поля разрешённой модели, уникальное в записи. `effectiveName` — выбранное моделью main name; `localName`, `fullName` и `propertyName` — итоговые runtime names. Для этого ограниченного профиля localName равен effectiveName, а fullName равен record.name + `.` + localName. Property names сохраняются явно: Value может сосуществовать с lookup ChosenName. Эти равенства — ограничения профиля, а не предположения о будущих providers. Full names всех слотов должны быть уникальны в артефакте.

`serialTypeId` — полная числовая идентичность SerialFieldType, включая representation bits. Имена в таблице объясняют идентичность и не являются сериализуемой заменой чисел на enum. Другие ID не поддерживаются этим локальным профилем, без выводов об их допустимости на wire.

| ID | Идентичность | Локальная проекция |
| --- | --- | --- |
| 0 | VOID | Только синтетическая int-позиция; никогда не логическое значение. |
| 8 | COMPACT_INT | Один int head. |
| 9 | BYTE_ARRAY | Один obj head. |
| 10 | UTF_CHAR_ARRAY | Один obj head. |
| 104 | LONG | Один int head, сразу за ним один VOID tail. |
| 120 | WIDE_DECIMAL | Один int head, сразу за ним один VOID tail. |
| 1 / 3 | BYTE / SHORT | Распознанные типы модели; только неуспешное локальное построение. |

`javaSlots` содержит ровно `int` и `obj`, массивы в порядке ordinal внутри категории. Каждый слот — `{ordinal, role, fieldId, fullName, localName, propertyName, serialTypeId}`. `ordinal` равен позиции в массиве. `role` — `head`, `tail` или `index-placeholder`. Head принадлежит одному логическому полю через `fieldId` и точно повторяет его три runtime names и полный type ID. Каждое логическое поле имеет ровно один head в правильной категории. Tail — int/VOID, ссылается на то же поле, что непосредственно предшествующий LONG/WIDE_DECIMAL head, и имеет зафиксированные имена `$VoidTail` (full/local name head плюс `$VoidTail`, property равен local name tail). Каждый такой head имеет ровно один tail; остальные heads не имеют tails. Index-placeholder — int/VOID с `fieldId:null` (нет логического значения) и именами record.name + `.$VoidTimeField`, `$VoidTimeField`, `$VoidTimeField`. В других местах VOID запрещён. Это позиции для сравнения, а не обязательные массивы или хранение C++.

`indexes` пуст тогда и только тогда, когда hasTime=false; иначе он содержит ровно два объекта `{position, fieldId}` для позиций 0 и 1. Каждая позиция соответствует этому int ordinal. Ненулевой fieldId должен владеть COMPACT_INT head в этой позиции; null означает index-placeholder. Хотя бы одна позиция должна быть настоящим индексом. Placeholder имеет ровно одного владельца-индекс и не может быть вне позиций 0/1. Обычные поля Second/First, не объявленные индексами, остаются логическими полями. Отсутствие и disabled-состояние объявлений индексов — разные исходные состояния, сохранённые в provenance, даже если позиция проецируется в одинаковый VOID. Object, long, duplicate и другие неизмеренные формы индексов не поддерживаются/отложены.

## Области поиска и валидация

Каждый lookup — `{scope, name, category, ordinal}`. `scope` — `record`, `scheme-int` или `scheme-obj`; `category` — `int` или `obj`; целевой ordinal разрешается в соответствующей категории javaSlots содержащей записи. Scheme scopes описывают API поиска во всём артефакте, категория должна соответствовать scope. Для компактности они хранятся вместе с целевой записью. Ключи уникальны в каждом record scope и среди всех записей для каждого scheme scope. Отсутствующий ключ не находит поле; null targets отсутствуют. Lookups могут указывать на синтетические слоты; их нельзя сводить к aliases логических полей. Порядок массива сохраняет порядок probes доказательств, но не меняет результат поиска.

Каждый слот имеет точные record lookups по full name и local name и scheme lookup по full name в своей категории. Дополнительные record keys задаются явно; запрещено автоматически создавать prefixed aliases или collapsed names. Примеры включают зафиксированные положительные ключи; проверка также сверяет все зафиксированные отрицательные probes. Полнота за пределами этих имён и профиля не заявляется. Отклоняются неразрешимые ссылки, повторяющиеся/конфликтующие ключи, неправильные scope/category, несовпадающие имена/типы head, неправильная принадлежность/порядок слотов и индексы. Порядок выданных записей сверяется с generation order после удаления disabled records, порядок логических полей — с active model order, а Java order — с неизменными slot rows; captured model HashMap traversal не используется как порядок записей. Структурная проверка этих документов не реализует XML resolution.

## Диагностика неуспешного построения

Каждая диагностика — `{code, stage, recognition, sourceRefs, subject, serialTypeId, evidenceRef, oracleStage}`. `sourceRefs` — упорядоченное подмножество ссылок inputs (пусто только при отсутствии входов); `subject` — непустой описательный локатор, а не local ID несуществующей схемы. `evidenceRef` — ссылка на TSV с точными Java exception class/message/origin; `oracleStage` — зафиксированная попытка `model.load` или `runtime.load`. `recognition` — `succeeded` (типы модели разрешены) или `not-reached` (нарушено предусловие входа). `serialTypeId:null` означает, что диагностика не относится к serial type, а не неизвестный числовой тип. Частичная успешная схема не публикуется.

| Зафиксированный случай | code / stage / recognition / type |
| --- | --- |
| S01-no-urls, обе попытки загрузчиков | `no-source-inputs` / `input` / `not-reached` / null. Две записи сохраняют разные oracleStage и сообщения в доказательствах. |
| S05-disabled-both | `all-index-fields-disabled` / `local-construction` / `succeeded` / null. Сохранено отдельное доказательство SchemeException. |
| S15-byte / S15-short | `unsupported-local-type` / `local-construction` / `succeeded` / 1 или 3. Утверждённое отклонение ADR заменяет случайный NullPointerException, сохраняя отказ. |

Эти сочетания code/stage — полный набор примеров отказов версии 1, а не универсальная классификация исключений. Другие отказы требуют отдельных доказательств и рассмотренного расширения контракта; скрытая переклассификация запрещена. Распознавание BYTE/SHORT не разрешает локальное построение, а отказ не запрещает их wire-коды. Для спроектированной диагностики не требуется равенство Java class/message; исходные наблюдения неизменны.

## Исключения и проверки

Peer/direction bindings, sender IDs, исходные requests и выбранные outgoing layouts исключены из identity локальной схемы. В частности, отсутствующий, исходно пустой и непустой request, выбравший ноль полей, остаются разными состояниями протокола ([P05](../protocol/CAPTURES.ru.md)); ни одно не представляется локальным `fields:[]`. Локальные слоты не являются wire layout. Отсутствие LONG/time-index VOID на wire — доказательство по исходникам, а не новая зафиксированная здесь проекция.

Imports, generators, alias collisions/removal, parser/default edge cases, known-event mappings, dxFeed properties/providers, rebuild isolation, conversions и dynamic/reset/PART/session behavior остаются неподдерживаемыми/отложенными в границах [NORMALIZED-MODEL](NORMALIZED-MODEL.ru.md) и [открытых вопросов](../../docs/upstream/OPEN-QUESTIONS.ru.md). Исходные метаданные сохраняются без приближённой реализации этих возможностей. Семантика программного построения C++ остаётся открытой.

Формальная JSON Schema и новые зависимости не добавлены. [Проверка](../../tests/conformance/check_json_contract.py) на стандартной библиотеке сверяет этот корпус примеров с TSV и проверяет выбранные недопустимые мутации; это не универсальный importer и не production validator. Контракт задают правила выше; точные выполненные проверки и ограничения находятся в [VALIDATION](examples/VALIDATION.ru.md).
