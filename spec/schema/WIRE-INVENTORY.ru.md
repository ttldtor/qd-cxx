# Обычная схема из wire-описаний

[English version](WIRE-INVENTORY.md). Английская версия является нормативной.

## Явная граница

`TapeReader(TapeLimits, TapeMode)` явно включает обнаружение обычной схемы.
Начальное состояние — проверенная пустая схема `EXTENDED_FIELDS_V1`. Допущены
только точные полные типы 2/8/10/40/56/72/88/120 из
[FIELD-TYPES](../encoding/FIELD-TYPES.ru.md). У созданных записей
`hasTime=false`: это обычное представление, не вывод индексов времени Java,
бизнес-полей, псевдонимов или отображений событий. Режим контейнера выбирается
отдельно и явно. Прежние средства чтения с заданной схемой, [статическое
связывание](../protocol/STATIC-BINDING.ru.md), проверка допуска и стандартные
профили сохраняют поведение. Обнаружение не включается автоматически по входным данным.

## Имена, идентичность и порядок источника

Точные имена записей в UTF-16 определяют локальные записи. Локальные ID следуют
первому появлению различных имён, независимо от разреженных ID отправителей.
Точные имена полей определяют логические поля внутри записи; первое появление
задаёт локальный порядок и полный тип поля. Новые имена добавляются без
перенумерации. Имена должны быть непустыми и корректно сформированными в UTF-16
согласно правилам `LocalSchema`; нормализация и автоматическое создание
псевдонимов не выполняются.

Разные ID отправителей могут описывать одну запись с перестановкой, подмножеством
или дополнительными полями. Объединение сохраняет каждое различное поле. Каждая
привязка контекста содержит действие для каждого исходного wire-поля в его порядке
и указывает на устойчивый локальный ID поля. Например, отправитель 90
`R(A:8,B:10)`, затем отправитель 7 `R(B:10,C:40,A:8)` создают локальную запись 0
с A/B/C и целевыми ID 0/1 и 1/2/0 соответственно. Исходные описания сохраняют
первоначальный порядок добавления, точные имена и типы полей.

Повтор имени поля внутри одного описания не поддерживается даже при равных типах:
обнаружение не может однозначно представить смысл такого источника. Повторное
использование имени записи/поля с другим полным типом не поддерживается. Биты
представления не маскируются. Повторные и переопределённые ID отправителей
по-прежнему отклоняются как некорректные. Прежний разбор сырых данных и поведение
повторных назначений при заданной схеме не меняются. При нескольких одновременных
дефектах общий приоритет ошибок не гарантируется.

Пустые записи и пакеты описаний допустимы. Отсутствующее исходное поле получает
прежнее значение по умолчанию — сырой ноль или null — в текущей форме объединения.
Ранее возвращённые записи не дополняются после появления новых полей. Чтобы
отличить отсутствие от присутствующего нуля, потребитель должен использовать
исходные описания и привязки.

## Владеющие снимки и отказ

Каждое успешное полное событие DESCRIBE_RECORDS, включая пустой пакет, создаёт
новую проверенную идентичность `LocalSchema` и полный `StreamDataContext`.
Все объявления источника, локальные имена, планы и значения по умолчанию для
кандидата подготавливаются до публикации. Само присваивание схемы и контекста,
а также обмен списков источников не выбрасывают исключений; между ними не
вызывается обратный вызов или внешний код. Атомарность действует на однопоточной
границе `feed`, а не гарантирует безопасность конкурентного доступа.

Любая ошибка разбора, профиля, схемы, ресурсов или выделения памяти сохраняет
прежние схему, контекст и список принятых источников. Списанные затраты и первая
терминальная диагностика при этом могут обновиться. Корректный префикс
отклонённого пакета описаний не публикуется. Входная память заимствуется лишь
на время `feed`; все сохраняемые имена находятся во владении.

`schema()` и `descriptions()` возвращают заимствованные неизменяемые представления
текущего владеющего хранилища. Представления контекста, планов, источников и схемы
становятся недействительными при успешном обновлении описаний, уничтожении,
перемещении или присваивании `TapeReader`. Отклонённые обновления сохраняют их хранилище
и идентичность. `schema().boundedCopy(limits)` явно сохраняет независимые объявления
с тем же происхождением. Ранее возвращённые токены `RecordContext` остаются
действительными для прежней идентичности и не удерживают `TapeReader`; они не
соответствуют следующему поколению обнаруженной схемы. Числовые локальные ID
устойчивы. Режим заданной схемы сохраняет исходное происхождение от вызывающей
стороны при обновлении описаний.

Каждая декодированная `StreamDataRecord` владеет точным неотрицательным `senderId`,
независимым от `localId` и происхождения. Добавленное в конец поле по умолчанию
равно -1 для созданных вызывающей стороной записей без идентичности источника;
прежние агрегатные инициализаторы сохраняют смысл. Это одно скалярное значение
фиксированного размера на выданную запись, охваченное ограничениями числа записей,
без выделения памяти и дополнительных списаний за значения полей. Прежние форматы
вывода его игнорируют. Поле не задаёт преобразование ID отправителя в локальный ID
и не разрешает выводить ID из других данных.

## Конечные ограничения допуска и построения

Все прежние ограничения кадров, исходных описаний, действий, имён и данных,
а также итоговые `SchemaLimits` остаются обязательными конечными границами;
ноль допустим. До ЛЮБОГО создания владеющих `LocalRecord` или резервирования
памяти по числу элементов проходы по заимствованным данным предварительно
проверяют всё итоговое объединение: записи, поля, ключи поиска, число единиц
UTF-16 каждого имени и всех имён вместе, корректность ключей и представимость
неотрицательных локальных позиций записей в int32. На каждое различное поле
создаётся один ключ поиска. Последующая проверка `LocalSchema::create` не заменяет
эту предварительную проверку. Резервирование по недоверенному числу элементов
не используется.

В режиме обнаружения `constructionUnits` дополнительно списывает затраты
на следующие допущенные этапы до выделения владеющей памяти и копирования;
учёт для заданной схемы не меняется:

| Этап | Логические затраты |
| --- | --- |
| Разбор сырого описания | Полное число байтов закодированной полезной нагрузки, включая неудачный разбор |
| Копирование сохранённого списка источников | На копируемую запись: 1 + число единиц имени + число полей + число единиц имён полей |
| Временные локальные объявления | S = число записей + число единиц имён записей + число полей + число ключей поиска + число единиц имён ключей поиска |
| Проверенная владеющая копия схемы | Повторно S |
| Новый контекст | Число планов источников + число действий источников + число локальных записей + число локальных значений по умолчанию |

Новые разобранные имена источников перемещаются в кандидата без повторного
списания за копирование. Каждой сырой записи и полю нужен структурный байт,
а число декодированных единиц UTF-16 не превышает числа байтов закодированных
символов. Поэтому полная полезная нагрузка даёт консервативную границу для
временных сырых элементов и имён. Подсчёт использует вычитание без переполнения.
Этап, для которого недостаточно бюджета, не выполняется. Ранее допущенные
затраты не возвращаются, в том числе при последующей семантической ошибке
или ошибке выделения памяти. Отказ терминален. Это логические единицы работы
и хранения, а не ёмкость выделенной памяти, суммарная работа по перемещению
векторов, такты процессора или измеренный RSS. Токены происхождения фиксированного
размера не удерживают исторические объявления схемы; `TapeReader` хранит только
текущий снимок.

## Ошибки и доказательства

Неподдерживаемые полные типы и конфликты типов дают UNSUPPORTED/TYPE на этапе
`wire-schema`; неоднозначные повторы полей — UNSUPPORTED/LOCAL_PROFILE на этапе
`wire-schema`. Некорректные ключи дают MALFORMED с подробностью `SchemaError`;
повторные ID отправителей — MALFORMED на этапе `binding` с INVALID_DESCRIPTION.
Ошибки конечных ограничений и выделения памяти сохраняют RESOURCE_LIMIT
и ALLOCATION_FAILURE в соответствующей контрольной точке построения, схемы
или привязки. Прежние диагностика и приоритет ошибок заданной схемы не меняются.

[Средство чтения](../protocol/TAPE-READER.ru.md), [CLI](../../docs/TAPE-INSPECT.ru.md) и
[целевая проверка](../../tests/conformance/protocol/wire-inventory/VALIDATION.ru.md)
описывают использование и фактически проверенные границы. Закреплённые
производственные эталоны STREAM/RAW со смешанными полями сравниваются по точным
именам полей и полным владеющим значениям: локальный порядок по первому появлению
в wire может отличаться от порядка явно заданной схемы. Синтетические тесты
с 48 записями дают дополнительные специально разработанные доказательства;
они не подтверждают совместимость с полным Java DataScheme, произвольными
типами сериализации или бизнес-событиями.
