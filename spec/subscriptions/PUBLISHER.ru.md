# Публикация и ретрансляция QTP

[English version](PUBLISHER.md). Нормативная версия на английском.

`qd/api/publisher.hpp` устанавливается с `qdcxx::feed`. Создайте `RuntimeBootstrap` на главном потоке перед запуском других потоков приложения, затем создайте `PublisherEndpoint`. Bootstrap должен жить дольше endpoint и использующих его экземпляров `ApiRuntime`. Endpoint владеет одним рабочим потоком и слушающим сокетом. После привязки сокета он возвращает фактический порт. Каждый принимающий endpoint Feed подключается в обычном режиме TICKER по отдельному TCP-соединению.

`getPublisher()` возвращает независимый объект публикации. `publish(quote)` копирует один прошедший проверку композитный Quote в ограниченную очередь либо возвращает диагностику. Объект публикации можно использовать из других потоков. `awaitDemand` ждёт появления или исчезновения точного символа в общем спросе. Символ входит в общий спрос, пока запрошен хотя бы одним клиентом. Поздний подписчик получает последнее значение, которое сохранялось при наличии другого подписчика. При последней отписке значение удаляется. Приём локального запроса на публикацию не подтверждает запись в сокет или доставку приложению. Завершение останавливает поток и освобождает сокеты и незавершённую работу. Повторная отправка через сохранённый объект публикации получает отказ.

Ключ общего спроса включает контракт, имя физической записи и точный символ.
`awaitDemand(family, recordName, symbol, ...)` наблюдает один ключ. Непустое имя, которое
никогда не попадает в объединение по выбранному контракту, считается отсутствующим, пока
endpoint обслуживает контракт. Вариант без имени записи ждёт присутствия символа в любой записи
выбранного контракта или его отсутствия
во всех записях. `getDemand(family)` копирует последнее опубликованное состояние спроса
по контракту, включая минимальную знаковую границу HISTORY в исходном представлении записи.
Копия владеет именами и символами и доступна после изменения спроса или закрытия endpoint.
Число строк ограничено произведением настроенного числа соединений и максимального числа
ключей на клиента. Методы наблюдают применённые подписки клиентов. Пока источник недоступен,
ретранслятор продолжает публиковать локальный спрос и повторно отправляет актуальные ключи
после переподключения.

## Фильтры спроса на соединение

`PublisherOptions::demand` задаёт политику по умолчанию с необязательными фильтрами
`ticker`, `stream` и `history`. `peerDemand` может полностью заменить эту политику для 32
различных числовых IP-адресов клиентов. IPv4 и его IPv4-mapped IPv6-представление обозначают
один адрес. Транспорт выбирает неизменяемую политику при приёме соединения. Идентификаторы
области IPv6, повторяющиеся адреса, имена DNS и динамические фильтры считаются ошибками
конфигурации. Пустой фильтр разрешает все ключи своего контракта. Клиенты с одним адресом
получают одну политику. По адресу фильтр не устанавливает личность клиента.

`FeedFilter::acceptRecord` применяет существующее выражение QD к имени физической записи и
исходному точному символу UTF-16. Например, `:Quote&IBM` разрешает запись `Quote` для `IBM`.
Учитываются данные рекорда и символа до преобразования в события. Отфильтрованные строки ADD
не попадают в состояние подписок и исходящий общий спрос. Превышение ограничения запроса к
фильтру закрывает только соответствующее соединение, не применяя пакет. REMOVE удаляет совпадающие
ключи из уже применённых подписок этого соединения. Повторная отписка или отписка от отклонённого
ключа не меняет спрос других клиентов.

### Замена политики действующего соединения

`getPeers()` возвращает идентификаторы активных соединений и последнюю ревизию политики каждого
клиента. `replacePeerDemand(id, policy)` ставит полную замену политики одного соединения в очередь.
Копия динамического `FeedFilter` передаёт неизменяемое поколение. Для применения следующего
поколения передайте его явно. Статические правила по адресам по-прежнему определяют начальную
политику новых соединений. По каждому контракту соединение хранит до 32 запрошенных ключей,
включая отклонённые фильтром. Для HISTORY сохраняется последняя исходная граница запроса. Ключ
сохраняется после применения команды подписки. Замена политики допускает ранее отклонённые
запросы и снимает ранее допущенные ключи, которые больше не разрешены.

Для endpoint одновременно ожидает исполнения одна замена. Истечение срока ожидания результата
сохраняет доступ к тому же объекту результата. Итоги замены — APPLIED, REJECTED или PEER_CLOSED.
Если применить замену не удалось за пять секунд, рабочий поток отклоняет запрос. APPLIED публикует
общий спрос всех затронутых контрактов и ревизию политики одновременно. Каждый самостоятельный
`getDemand(family)` читает последнюю опубликованную версию своего контракта. Серия отдельных
вызовов может увидеть дальнейшие изменения. REJECTED сохраняет предыдущую политику.

Перед кодированием DATA поток проверяет допуск физической записи. Замена исключает отклонённые
записи из очереди, в том числе подготовленный кадр, пока запись байтов ещё не началась. Если отмена
допуска прервёт частично записанный DATA-кадр или уже начатый снимок либо транзакцию HISTORY,
endpoint закрывает выбранное соединение и возвращает PEER_CLOSED. Из общего спроса снимаются
ключи этого соединения. Подписки и политики остальных клиентов действуют дальше.
При сбросе источника уже начатый снимок или транзакция HISTORY также требует закрыть
соединение с этим клиентом до отправки DATA нового поколения.

Для TICKER и STREAM удерживаемый пакет доставки сохраняет взаимный порядок разрешённых строк.
Если ещё не начатый DATA-кадр содержит строку, которая стала запрещённой, весь кадр отбрасывается,
а разрешённые строки заново кодируются из того же пакета. Незатронутый кадр сохраняется.
Уведомление tracker или вызов `getCurrentFilter()` сами по себе не меняют политику клиента и спрос
источнику: текущее неизменяемое поколение нужно передать в `replacePeerDemand`. Согласование с
источником использует получившееся объединение эффективного спроса, включая самую раннюю оставшуюся
границу HISTORY других клиентов. Эта граница действует для поддержанных профилей publisher с
точными ключами и не расширяет [поддержку выражений фильтра](FEED-FILTERS.ru.md).

Каждый клиент присылает `DESCRIBE_PROTOCOL` и описания своих записей до отправки подписок. Endpoint сопоставляет ID в описании клиента с локальной композитной записью `Quote` и отправляет собственное `DESCRIBE_RECORDS` до DATA. Кортежи подписок для описанных неподдерживаемых записей пропускаются. Этот профиль использует обычный TCP и QTP с точными символами и композитным Quote. По умолчанию сокет слушает числовой IPv4 loopback на свободном порту. Допускается не более восьми активных или завершаемых клиентов, 32 применённых ключей на контракт и клиента, 256 декодированных кортежей в кадре подписки и 1024 запросов в очереди публикации. Пределы количества клиентов и запросов можно уменьшить в конфигурации. Переполнение очереди клиента, ошибочный вход или невозможность записи в течение десяти секунд завершает это соединение. Остальные клиенты сохраняют свои подписки и продолжают получать данные. TICKER может объединять ожидающие обновления одного символа.

Допускаются непустые точные символы длиной до 256 единиц UTF-16. Время bid и ask кодируется знаковыми 32-битными секундами. Каждое из этих значений должно быть кратно 1000 мс. `timeMs` лежит в пределах секунды более позднего времени bid или ask. Младшие 22 бита sequence и знаковая наносекундная часть передаются в дополнительных полях `Sequence` и `TimeNanoPart`. Endpoint передаёт четыре исходных значения wide decimal и оба кода биржи. При публикации отклоняются преобразованные числовые значения со снимком проекции, ненулевой `eventTime` и другие значения вне этого профиля. Встроенный реестр Feed поддерживает восемь стандартных полей Quote. Чтобы принимать полную точность времени и sequence, добавьте два дополнительных поля в явный входной реестр.

См. [общий спрос сервера](SERVER-DEMAND.ru.md), [входящие подписки](../protocol/INCOMING-SUBSCRIPTIONS.ru.md) и [документацию Java DXPublisher](https://docs.dxfeed.com/dxfeed/api/com/dxfeed/api/DXPublisher.html) по поведению общего спроса и последнего значения.

## Отдельный источник

Укажите числовой TCP-адрес и порт в `PublisherOptions::source`, чтобы
ретранслировать композитный Quote от отдельного QTP-источника. В этом режиме
локальная публикация возвращает `INVALID_STATE`, очередь публикации не создаётся.
Слушающий порт доступен и после потери источника. Сессия объявляет приём TICKER
DATA и отправку ADD/REMOVE. До первой подписки она передаёт локальное описание
Quote. Подписки к источнику кодируют символы в каноническом Penta там, где оно доступно, и в UTF-16 в остальных случаях. Источник объявляет собственный идентификатор записи и поля DATA.
Ретранслятор принимает до 32 сопоставленных композитных Quote в кадре с
поддерживаемыми точными представлениями полей.

Первый заинтересованный клиент добавляет ключ у источника, последняя отписка
удаляет его. Ретранслятор отмечает отправку, когда локальный транспорт TCP
принял весь кадр. Источник может независимо наблюдать входящую команду.
`getSourceStatus()` сообщает последнее согласованное поколение и состояние
соединения. `awaitSourceGeneration()` ожидает нового поколения до заданного
срока. Эти методы не ждут доставки конкретной подписки источнику.

При сбое ретранслятор сбрасывает вход, кеш и очереди прежнего поколения,
выдерживает заданную задержку повторного подключения и после сброса коллектора
открывает новую сессию. Текущий спрос объявляется заново. Регистрации клиентов
обычно сохраняются. Если сокет клиента уже принял префикс старого кадра DATA,
ретранслятор закрывает это соединение для сохранения целостности фрейминга.
Полностью принятые байты могут дойти до клиента. Поколение служит локальной
диагностикой, непрерывность доставки при восстановлении не гарантируется.

## Смешанный профиль

Перед созданием источника или ретранслятора установите `PublisherOptions::mixed`
в `true`. Endpoint объявляет TICKER Quote, STREAM TimeAndSale и HISTORY Order
источника DEFAULT в одной сессии QTP. Контракты хранят отдельные подписки и
ёмкости доставки. У каждого клиента свои регистрации и остаток неполной записи.
Для HISTORY нужно согласовать опцию снимков `hs`.

`Publisher::publish` принимает все три типа событий. STREAM доставляет отдельные
события по порядку, включая одинаковые. HISTORY использует знаковые границы в
исходном представлении. Коллектор формирует флаги снимков и транзакций, а удаление
сохраняет индекс записи. У DEFAULT Order индексы от нуля до `INT32_MAX` и нет
суффикса источника. END и SNIP используют индекс ноль. `awaitDemand(family, ...)` наблюдает объединённый спрос по
точному символу в одном контракте. Публикация отклоняет поля и метаданные, которые
не помещаются в поддерживаемые физические раскладки. Локальный TimeAndSale принимает
нулевые флаги события и необязательное поле наносекунд. Входящий DATA от источника
допускает до 32 сопоставленных записей в кадре. У каждого клиента 32 места доставки
на контракт. HISTORY разделяет до `16 * maxConnections * 32` индексированных точек
между клиентами и ключами.

## Ретрансляция полного каталога записей

Передайте в `PublisherOptions::catalog` бинарную схему и упорядоченные QTP-имена полей.
Задайте `source`, оставив `mixed` равным false. До запуска endpoint проверяет полный
исходящий дескриптор, затем владеет копиями схемы и имён полей. Используйте
`loadBinaryJsonSchema` и `loadBinaryJsonWireNames` с парой файлов из одного
[экспорта default или dxlink](../../tools/schema-export/README.ru.md). C++ publisher
принимает типизированную конфигурацию и работает без библиотеки JSON.

Любую физическую запись можно запросить в TICKER и STREAM. Для HISTORY также нужны
индексная раскладка и согласованная опция `hs`. В каждом направлении ID отправителя
сопоставляются с физическими записями каталога. Ретранслятор декодирует DATA в записи,
распределяет их по контракту и подписке и кодирует по собственному дескриптору.
Nullable-поля, имена записей разных источников и знаковые индексы удаления HISTORY
сохраняются. Каждый коллектор применяет свои правила снимков, схлопывания,
транзакций и очередей.

Полный дескриптор должен помещаться в один кадр QTP размером до 64 КиБ. Здесь действуют
те же пределы endpoint: 32 ключа на клиента и контракт, 256 кортежей на кадр
подписки. Входящий кадр DATA может содержать до 32 сопоставленных экземпляров записей, в том числе с одним общим ключом. Кадр сверх этого предела завершает текущее соединение с источником, а при переподключении спрос отправляется повторно. Используйте источник, который объявляет все три контракта QTP и поддерживает `hs`.

Для профиля локального каталога см. [публикацию физических записей](RECORD-PUBLICATION.ru.md).

Выбранный проект изменения внутренней очереди описан в
[ADR-0016: Очередь целых публикаций](../../docs/decisions/ADR-0016-whole-publication-queue.ru.md).
Его интеграция и сравнительные замеры ещё предстоят.
