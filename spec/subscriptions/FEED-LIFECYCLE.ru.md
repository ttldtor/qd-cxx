# Отключение endpoint, reconnect и очистка

[English version](FEED-LIFECYCLE.md). Нормативный текст — английский.

Контракт дополняет [публичный feed API](../../docs/FEED-API.ru.md). Намерение
подключения, физическое завершение native-операций, сброс источника и quiescence
обработчиков — разные наблюдения. `NOT_CONNECTED` означает логическое отключение;
это не подтверждение native retirement и не барьер завершения очистки кэша.

## Принятые операции

`disconnect()` немедленно фиксирует `NOT_CONNECTED` и запрещает новый ввод старой
native-попытки. Сохраняются желаемые интересы, ID подписок/обработчиков и уже
спроецированный кэш SDK. Повторное отключение ничего не меняет. `connect()` с первым
принятым фиксированным адресом возобновляет работу с новой эпохой источника. Другой
адрес по-прежнему отклоняется. `reconnect()` запрашивает новую попытку только при
логически включённом подключении; до первого connect и после явного disconnect
ничего не делает. `disconnectAndClear()` дополнительно сохраняет запрос очистки,
в том числе при уже отключённом endpoint. Неизменное состояние не создаёт повторного
уведомления. Все три метода ничего не делают в поглощающих `CLOSED` и `FAILED`.
`connect()` на terminal endpoint по прежнему контракту отклоняется.

Producer-вызовы потокобезопасны и допускаются из callback. Они не выполняют native
работу и обработчики непосредственно в вызывающем потоке. Физические намерения
могут объединяться; принятые различные наблюдения состояния и очистка сохраняются.
Уже выбранный полный снимок event listeners может завершиться после вызова управления
из одного обработчика. Прежние правила close/исключения event listener действуют
и для такого обхода снимка.
Управление сохраняет нормализованный выбор типов каждой подписки, включая
`RegisteredEvent`. Source/clear eligibility проверяется до выбора формы delivery.

## Конечный приём уведомлений

Положительный `RuntimeOptions::maximumPendingStateChangesPerEndpoint` по умолчанию
равен 8. Endpoint до публикации выделяет фиксированное кольцо. Ожидающие,
исполняющиеся и освобождаемые выбранные снимки используют общую ёмкость. Переход
резервирует слот и непереиспользуемую ревизию управления до изменения состояния,
намерения, очистки или delivery fence. Исчерпание вызывает `api::Error` с
`RESOURCE_LIMIT`, не меняя перечисленных наблюдений. Операции без различного
перехода слот уведомления не нужен, но изменение намерения требует новой ревизии.

Слот занят до освобождения lease выбранного снимка, включая вызванное последним
освобождением уничтожение захватов приложения. Уничтожение происходит вне control
locks. Отдельная ёмкость объектов state listeners занята до их фактического последнего
уничтожения. Worker до дальнейшего progress endpoint доставляет конечное число
уведомлений, ограниченное ёмкостью; reentrant добавления не продлевают обход
бесконечно. Для close/failure сохранён зарезервированный путь даже при заполненном
кольце. Ранее принятые наблюдения предшествуют последующим native и terminal
наблюдениям. Регистрация, удаление, изоляция исключений и retirement terminal
observers описаны в [контракте состояния](FEED-STATES.ru.md). Ожидающий состояние
просыпается при публикации до вызова observers; [current-state waits](FEED-WAITS.ru.md)
не меняются.

## Сохранённый кэш и идентичность источника

Обычная пауза завершает native-попытку и освобождает не принятый в очередь decoded
input, не сбрасывая стабильные adopted queues и их спроецированный кэш. Только
после настоящей native quiescence `SUSPENDED` кэш может доставляться новым/изменённым
подпискам offline. Сохраняется исходная идентичность очереди/эпохи. Доставку
разрешает точная ревизия принятой паузы; clear и resume немедленно отменяют разрешение.
Удерживаемому старому native offer никогда не присваивается новая ревизия.
Producer-запрос немедленно запрещает новую публикацию. Последующее сериализованное
действие нижнего owner устанавливает границу сохранённого кэша и запрашивает
оплаченное работой освобождение ещё не зафиксированного source offer до нового staging.
Уже начатая непрерываемая проекция может завершиться; зафиксированный кэш не
откатывается. Это не снимок кэша в момент внешнего вызова по часам приложения.
При исчерпании работы cutoff сохраняется, новый source offer отклоняется до
завершения disposal. Обычная пауза не подменяется сбросом источника или эпохи.

Retained progress использует неизменяемое локальное происхождение доставки.
Ранее поставленные в очередь source/live/initial уведомления, включая TICKER initial
до паузы, не превращаются в replay кэша. Offline callback может начаться только для
cached INITIAL, заново построенного в retained-cache progress. Старый невыбранный
FIFO освобождается с настоящими work/discard/gap счётчиками. Последующий final drain
сохраняет этот fence; обычный close без прежней паузы сохраняет прежнее правило
префикса. Выбранные callbacks и собственные leases приложения не меняются.
Clear немедленно запрещает каждый новый выбор устаревших событий. Затем worker
выполняет настоящий сброс очереди/источника и необходимые ACK. Отдельного публичного
ожидания физического завершения clear этот API не предоставляет. Будущие методы
last-value/snapshot обязаны проверять принятую ревизию clear до чтения сохранённых
данных: нельзя выдавать старый кэш до физического подтверждения сброса. Текущий
публичный facade предоставляет event delivery, а не запрос last-value кэша.
Отдельный clear после завершённого сброса требует нового настоящего сброса,
эпохи очереди и свежих notices/ACK; прежний global ACK не используется повторно.
Запросы во время незавершённого reset по-прежнему могут объединяться.

Resume/reconnect выполняет настоящий сброс старого источника до создания новой
попытки. Обычный disconnect сохраняет кэш на отключённом интервале, но не обещает
сохранения при переходе к свежей эпохе. Желаемые интересы и ID регистраций переживают
сброс. Replay convergence/emitted сбрасываются даже при прежнем составе интересов,
поэтому свежий peer получает реальные ADD. Lifecycle-вызовы не пополняют попытки
фабрики, работу, ID действий и конечные квоты. Копии Event приложения и неизменяемые
retained batches остаются действительными и учтёнными своими исходными leases при
pause, clear, reconnect и окончательном close. Обычный close окончателен.

Старый результат poll не может публиковать `CONNECTED`/`CONNECTING` или выбирать
новые старые данные после более свежего producer fence, включая быстрые
 disconnect/connect. Публикация native state и выбор события проверяют точную
ревизию под endpoint mutex. Выбор берёт endpoint mutex перед subscription mutex;
ни вызов приложения, ни уничтожение его захватов не происходят под этими locks.

## Совместимость с Java и нижнее управление

Закреплённая [реализация Java](https://github.com/devexperts/QD/blob/0ddc0a09779fb61d74cc0b37c6449ff47dcb715f/dxfeed-impl/src/main/java/com/dxfeed/api/impl/DXEndpointImpl.java#L378-L396)
сначала останавливает и ожидает, очищает ticker/history и отключается. C++ сохраняет
немедленное принятое логическое отключение и offline replay кэша, но физическая
очистка асинхронна по описанным выше правилам. Значения событий приложения остаются
собственными значениями. Прежнее отличие неблокирующего `connect()` и доставки
observers C++ явно сохранено в [FEED-STATES](FEED-STATES.ru.md).

Нижний caller-driven plain `TcpRecovery` предоставляет `requestDisconnect(clear)`
и `requestReconnect()`, `RecoveryPhase::SUSPENDED` и
`RecoveryStatus::sourceResetPending`; см. [bounded recovery](../transport/RECOVERY.ru.md).
Публичный feed по-прежнему владеет worker: приложению не нужен polling нижнего owner.
TLS policy, семейства событий и владение process/bootstrap не меняются.
