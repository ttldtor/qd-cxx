# Ожидание текущего состояния публичного feed API

[English version](FEED-WAITS.md). Английский текст является нормативным.

`Endpoint::awaitState` и `Subscription<Event>::awaitState` ожидают текущее
состояние жизненного цикла без опроса приложением. Параметры: целевое состояние,
абсолютный срок `std::chrono::steady_clock::time_point` (по умолчанию `max()`)
и `std::stop_token` (по умолчанию пустой). Методы не подключают и не закрывают
объект, не выполняют сетевую работу, не регистрируют наблюдателей и не расходуют
ёмкость listeners. Подключение, восстановление и доставку событий выполняет
существующий SDK worker.

## Наблюдение и результат

`StateWaitResult<State>` содержит `status`, точное наблюдаемое `state` и первую
диагностику жизненного цикла `diagnostic`; снимок копируется под mutex публикации
состояния. Диагностика advisory-наблюдателей состояния остаётся отдельной.
Условия проверяются в следующем порядке:

| Условие при наблюдении под mutex | `WaitStatus` |
| --- | --- |
| Текущее состояние равно целевому | `REACHED` |
| Текущим является другое `CLOSED` или `FAILED` | `TERMINAL` |
| У token запрошена остановка | `CANCELLED` |
| Срок steady clock истёк | `DEADLINE_EXPIRED` |

Этот порядок действует и до первого засыпания. Уже достигнутая цель имеет
приоритет над отменой и истёкшим сроком; другое поглощающее терминальное состояние
имеет приоритет над ними обоими. Отмена имеет приоритет над сроком. После снимка
состояние может конкурентно измениться. Цель `FAILED` может быть достигнута обычным
образом: диагностика результата описывает фактический сбой жизненного цикла,
а не исключение из самого ожидания.

Это условия **текущего состояния**, без запоминания переходов. Например,
`awaitState(CONNECTING)`, вызванный после перехода endpoint в `CONNECTED`,
не завершается успешно из-за прежнего прохождения через `CONNECTING`. Он ждёт
повторного текущего состояния либо другого условия завершения. Если важен каждый
выбранный переход, используйте [наблюдателей состояния](FEED-STATES.ru.md).
`NOT_CONNECTED` и `CONFIGURED` могут совпадать уже до `connect()`.

`CLOSED` по-прежнему подтверждает освобождение native-состояния/регистрации
и захватов event listeners. Подключённые наблюдатели состояния ещё могут выполняться
или освобождать захваты. Поэтому результат `awaitState(CLOSED)` **не является
барьером quiescence**. Существующий `closeAndAwaitTermination()` на потоке-создателе
возвращает фактический detached `CloseResult` после освобождения всех native owners
и event/state captures. Его семантика drain сохраняется; срок или отмена ожидания
состояния не меняют drain allowance endpoint и не задают жёсткую границу времени
завершения процесса.

## Потоки, время жизни и ошибки

Вызывать ожидания может только поток-создатель runtime, в том числе для handles,
переживших facade endpoint или runtime. Чужие потоки и SDK callbacks получают
`api::Error` / `WRONG_THREAD`. Callback или деструктор захвата на потоке-создателе,
выполняющийся в контексте освобождения **любого** endpoint, получает
`INVALID_STATE`, в том числе для другого endpoint и уже совпадающей цели.
Эти проверки предшествуют быстрому возврату готового результата. Существующее
поведение `closeAndAwaitTermination()` при освобождении другого endpoint сохраняется.

Неверное значение enum состояния даёт `api::Error` / `INVALID_ARGUMENT`.
Отмена, другое терминальное состояние и истечение срока — обычные результаты;
они не вводят другую transport error и не меняют диагностику жизненного цикла.
Native-сбои C++ mutex/condition могут передаваться как `std::system_error`,
как и у существующего блокирующего ожидания освобождения. Планирование приложения
или ОС может задержать возврат.

Detached port имеет сильного владельца до завершения снятия stop callback.
Регистрация выполняется до захвата mutex port, поскольку уже отменённый token
может немедленно вызвать callback. Callback синхронизируется с тем же mutex
перед уведомлением. Все публикации состояния используют этот mutex и уведомляют
до вызова наблюдателей. Ожидающий поток освобождает lock до уничтожения stop callback,
поскольку снятие регистрации может ждать конкурентный поток, запросивший остановку.
Это закрывает окна потери пробуждения между проверкой условия и засыпанием без
очереди переходов, цикла опроса, detached worker и вызова кода приложения под control lock.

## Отмена в консольном приложении

[Самостоятельный пример](../../examples/feed_quote/README.ru.md) ожидает `CLOSED`
endpoint, терминальный сбой, срок получения или общий stop token. Наблюдатель сбоя
подписки владеет копией `std::stop_source` приложения и запрашивает отмену. Такой
сбой остаётся ошибочным завершением; только реальное прерывание ОС даёт код 130.
Ожидание не продвигает feed.

SDK не устанавливает обработчиков сигналов процесса. Scoped-объект `SignalStop`
примера создаётся после bootstrap `ApiRuntime`, до первого ленивого SDK worker
и других потоков приложения. На POSIX он сохраняет маску потока-создателя и полные
dispositions `SIGINT`/`SIGTERM`/`SIGPIPE`, блокирует сигналы прерывания/завершения,
устанавливает известные неигнорируемые dispositions для `sigwait` и игнорирует
`SIGPIPE`, пока выполняются вывод/native-работа. Обычный reader вызывает
`request_stop`; асинхронный обработчик сигнала этого не делает. При освобождении
`SIGTERM` направляется только своему ещё живому reader thread; синтетическое
пробуждение отличается от реального прерывания. После join восстанавливаются
сохранённые dispositions и маска. Реальные pending signals при гонке с восстановлением
сохраняют семантику прежней политики ОС.

В Windows пример обрабатывает только Ctrl+C/Break. Console callback сигнализирует
собственное событие под SRW lock со временем жизни процесса; обычный reader
запрашивает остановку. Снятие обработчика и эксклюзивное обнуление заимствованного
handle исключают уже вошедшие или поздние callbacks перед native close.
Закрытие консоли/logoff/shutdown сохраняют прежнее поведение ОС; корректный drain
при принудительном завершении консоли не обещается.

Cleanup guard на основном потоке завершает работу SDK, пока bridge и захваты
вывода живы, в том числе при раскрутке исключения после `connect()`. Частичная
конструкция bridge откатывает каждую установленную маску, disposition, handler
и handle. Деструктор будит reader и без прерывания; невосстановимый native отказ
освобождения завершает процесс вместо оставления живого потока или висячего handler.
Справка без аргументов/на английском/русском возвращается до bootstrap и установки
обработки сигналов.

## Доказательства совместимости

Зафиксированный [Java QD source](../../upstream.lock),
[`DXEndpoint.java:783–820`](https://github.com/devexperts/QD/blob/0ddc0a09779fb61d74cc0b37c6449ff47dcb715f/dxfeed-api/src/main/java/com/dxfeed/api/DXEndpoint.java#L783-L820),
различает завершение жизненного цикла (`awaitNotConnected`) и завершение обработки,
предупреждая об ожидании на executor endpoint. Результат текущего состояния C++,
срок steady clock и stop token явно расширяют это разделение; тождество Java
методов/типов и реализация Java `awaitProcessed` не заявляются.

Время жизни отмены следует C++ [контракту регистрации/снятия stop callback](https://eel.is/c++draft/stoptoken.concepts).
Platform bridge использует [наследование POSIX thread signal mask](https://man7.org/linux/man-pages/man3/pthread_sigmask.3.html),
[`sigwait`](https://man7.org/linux/man-pages/man3/sigwait.3.html),
[направленный потоку `pthread_kill`](https://man7.org/linux/man-pages/man3/pthread_kill.3.html)
и [контракт console handler Microsoft](https://learn.microsoft.com/en-us/windows/console/setconsolectrlhandler).
