# Спрос к источнику и доставка клиентам

[English version](SERVER-DEMAND.md). Английский текст нормативный.

Владелец сервера открывает одну `MuxQueue` для каждого поддерживаемого контракта. У каждого клиента своя регистрация и отдельные резервы для команд, записей и удерживаемых пакетов. Владелец последовательно выполняет операции с очередями и спросом, передавая конечные бюджеты работы. Фоновых потоков у этих компонентов нет.

Полные кадры ADD/REMOVE декодирует [декодер входящих подписок](../protocol/INCOMING-SUBSCRIPTIONS.ru.md). Передайте полученный пакет в `MuxQueue::submitIncomingSubscription` с регистрацией клиента. Очередь проверяет владельца регистрации и соответствие сообщения контракту. При отказе ни одна запись пакета не ставится в очередь. Принятая команда владеет копией всего входа. После `progress` проверьте её результат, чтобы отличить применение от отказа или отмены. Применение меняет объединённый спрос. Если коллектор ещё синхронизируется, `admit` может вернуть `BUSY`, сохранив событие у вызывающей стороны.

`DemandTracker` сверяет точный объединённый спрос одного контракта из `MuxQueue::aggregateEntries()` или `MuxState::aggregateEntries()` со спросом, уже принятым текущим выходом к источнику. Ключ состоит из идентификатора записи в схеме и точного UTF-16 символа. Первый активный клиент для ключа даёт один ADD. Дополнительные клиенты с тем же ключом не создают дубликат ADD. Последняя отписка или закрытие регистрации даёт один REMOVE. Если ключ HISTORY остаётся активным и меняется минимальная сырая граница, ADD заменяет прежнюю границу без предварительного REMOVE. Изменения между наблюдениями могут объединиться в конечное желаемое состояние.

`next` возвращает одно изменение с неповторяемым локальным номером. Пока оно ожидает подтверждения, следующие вызовы возвращают то же изменение с исходным текстом. Передайте его писателю и подтвердите номер, когда владелец выхода принял команду целиком и завершит её отправку в порядке очереди. Подтверждение меняет только локальное состояние выхода. При потере поколения источника отбросьте его незавершённый вывод и сбросьте tracker. Следующий вызов начнёт с пустого подтверждённого спроса и повторно отправит текущее объединение. Чтобы продолжить после частичной записи в живое соединение, завершите эту команду или закройте соединение.

Оба банка резервируются при создании. На проверку и сравнение выделяется явный бюджет. При отказе подтверждённый спрос и незавершённое изменение сохраняются. Текст результата заимствован до подтверждения, сброса, перемещения или уничтожения. Вызывающий код передаёт полное объединение уникальных ключей от сериализованного владельца. В резервах сервера учитываются два банка на каждый tracker.

Потребитель клиента может удержать один `OwnedMuxBatch` для частичной записи и вернуть `PAUSE`. После полной отправки освободите пакет и запросите возобновление. При сбое соединения освободите пакет, запросите аварийное закрытие этой регистрации и продолжайте `progress` до её терминального результата. Другие регистрации сохраняют собственный спрос и ограниченную доставку. TICKER может объединять ожидающие обновления одного ключа. При `storeEverything=false` поздний клиент получает последнее значение, пока другая регистрация держит ключ. Последняя отписка удаляет это значение из кеша.

Переходы при первой подписке и последней отписке соответствуют поведению Java QD. Эталон для пересекающихся подписок и спроса к источнику описывают [QDCollector](https://github.com/devexperts/QD/blob/0ddc0a09779fb61d74cc0b37c6449ff47dcb715f/qd-core/src/main/java/com/devexperts/qd/QDCollector.java) и [QDDistributor](https://github.com/devexperts/QD/blob/0ddc0a09779fb61d74cc0b37c6449ff47dcb715f/qd-core/src/main/java/com/devexperts/qd/QDDistributor.java). Новых типов сообщений QTP адаптер не вводит.
