# Бюджеты ресурсов и ограничения числа записей

[English version](RESOURCE-LIMITS.md). Нормативный текст — EN.

Этот контракт классифицирует существующие ограничения приёма, callback,
коллекторов и локального издателя. Текущая реализация и принятая политика замены
описаны отдельно. Публикация документа не включает замену. Существующие пределы
продолжают защищать хранилища, пока замена не пройдёт описанные ниже проверки.

Доступный API описан в [контракте получателя](RECEIVER.ru.md),
[контракте очереди Mux](../mux/QUEUES.ru.md) и
[контракте публикации](RECORD-PUBLICATION.ru.md). Generic-получатель и профиль
приёма высокоуровневого Feed — разные уровни; предел профиля не становится
ограничением протокола QTP.

## Роли ограничений

| Роль | Значение | Принятая политика |
| --- | --- | --- |
| Семантический предел результата | Явный запрос ограничивает требуемый результат. `HistorySnapshotOptions::maximumResults` по умолчанию задаёт 128 возвращаемых значений; больший результат завершается явной ошибкой. | Сохранить описанную семантику результата и завершения. Память результата учитывать независимо. |
| Квант работы | Шаг progress обрабатывает конечную порцию, затем даёт возможность работать другим участникам. | Сохранить конечные бюджеты работы в байтах/времени; число записей может помогать планированию. Продолжать оставшуюся принятую работу без ожидания заполнения порции. |
| Ограничение хранилища реализации | Массив, индекс, резерв пакета или заранее выделенная очередь имеет проверенную конечную ёмкость. | Сохранить защиту до появления замены с независимым учётом. По возможности выводить ёмкости представления из байтовых бюджетов с проверкой арифметики. |
| Случайный предел допуска | Число отклоняет допустимый ввод при наличии места в соответствующих байтовых бюджетах без семантической причины. | Заменить общий допуск по числу записей независимыми байтовыми бюджетами, описанными ниже. Одно увеличение числа не реализует эту политику. |

Один параметр сейчас может выполнять несколько ролей. Его роль в планировании
не обосновывает общий предел допуска. Эти числа описывают локальную политику C++
и не устанавливают соответствующих ограничений Java QD или wire-протокола.

## Текущие ограничения приёма и callback

| Предел и текущее значение | Назначение и фактическое действие | Настройка или замена |
| --- | --- | --- |
| `EndpointOptions::batchRecords`, от 1 до 4, по умолчанию 4 | Выбирает полные физические записи для одного callback, задаёт размер пакетов очереди и квант маршрутизации network STREAM. Работа проекции и резервы custom-пакета используют предел времени компиляции 4 независимо от выбранного значения; выбор 1 не уменьшает резерв пакета. Этот квант работы действует в пределах проверенного хранилища. | Настраивается при создании endpoint. Заменять жёсткий предел профиля после независимого обеспечения ёмкости в байтах и работы для дескрипторов пакета, спроецированных значений и подготовки пакета. |
| `EndpointOptions::pendingRecords`, от 1 до 128, по умолчанию 128; не меньше `batchRecords` | Резервирует места отсоединённых записей каждой подписки и участвует в общей ёмкости очереди. Дополнительно действуют независимые байтовые пределы записей/пакетов. Число мест может исчерпаться раньше байтов; это предел допуска, поддержанный текущим конечным хранилищем. | Настраивается при создании endpoint в проверенном диапазоне. Заменить общую квоту строк допуском по байтам каждого потребителя и ёмкостью дескрипторов/индексов, выведенной из бюджета; сохранить удержание целого пакета и учёт старых поколений. |
| `CallbackSlotPool::PHYSICAL_RECORDS = 4`, `MAXIMUM_EVENTS = PHYSICAL_RECORDS * core::MAX_DELIVERY_PROJECTIONS` | Ограничивает максимальное число типизированных проекций. Пул заранее учитывает консервативный запас payload в 1 МиБ и память пакета/зарегистрированных событий. Статическая проверка покрывает худший поддержанный случай текста и непрозрачного payload. Работа проекции также выведена из предела физических записей. | Внутренний проверенный расчёт хранилища без отдельного публичного параметра числа записей. Заменять вместе с резервированием пакета и расчётом работы проекции. Одного расширения проверки endpoint недостаточно для безопасности. |
| Идентичности custom callback и одновременные резервы пакетов | Вектор слотов пула получает размер один раз. `RuntimeOptions::maximumCustomCallbackSubscriptions` и `maximumCallbackBytes`, по умолчанию 16 и 32 МиБ, ограничивают резервы вместе с фиксированной памятью идентичностей. Устаревшая задача executor удерживает идентичность/поколение, а не прежний пакет. События типизированного пакета хранятся во владеющем векторе. | Пределы задаются при создании runtime. Сохранить конечное хранилище идентичностей и проверку поколений; до подготовки/передачи независимо резервировать фактически удерживаемую ёмкость каждого пакета. Идентичности слотов не заменяют учёт payload. |
| `TAPE_FRAME_RECORDS = 64` | Локальный tape-профиль выделяет работу полного декодирования DATA, поля и память исходных записей для 64 записей. Это ограничение декодирования/допуска, а не только квант callback. | Внутренняя константа профиля. До снятия предела перевести локальный профиль на проверенную байтовую границу ввода и расчёт расширения декодированных данных. Сохранить обработку повреждённого/неполного ввода и владение полным событием. |
| `STREAM_ROUTE_RECORDS = 16` | Ограничивает маршрутизацию источника за один шаг progress очереди в использующих это значение профилях. Network STREAM вместо него использует `batchRecords`, согласуя продвижение префиксов с выборкой callback. | Внутренний квант работы. Сохранить возобновляемость и справедливое обслуживание; более крупное принятое событие не должно отклоняться из-за нескольких шагов маршрутизации. Общую роль в расчёте размеров заменяют бюджеты работы в байтах/времени. |
| Ёмкости строк network DATA из `sizeNetworkData` | `maximumReceiveMessageBytes` задаёт от 8 192 до 65 536 байт типа и payload. Число полных строк консервативно ограничено `(messageBytes - 1) / 2`; одна дополнительная попытка обработки покрывает неполный суффикс. Расширение декодированного хранилища учитывается отдельно. | Байтовая граница входящего сообщения задаётся при создании endpoint. Поддерживать согласованность производных ёмкостей индексов/работы с этой границей и расширением локальных полей. Производное число ограничивает представление и не является дополнительной независимой квотой строк. |

Расчёт сетевой байтовой границы не снимает предел локального tape-профиля или
пределы callback/ожидающих записей. Он также не доказывает отсутствие владеющих
проекций в типизированной доставке: текущий путь custom executor подготавливает
владеющие значения событий до передачи callback.

| Предел и текущее значение | Назначение и фактическое действие | Настройка или замена |
| --- | --- | --- |

`PublisherRecordLimits::rowBytes` ограничивает одну логическую строку каталога.
`pendingBytes` учитывает привязку INPUT и полное хранилище публикации в локальном
режиме каталога и явном режиме `streamBytes`. Прежний типизированный издатель без
байтового режима выводит ёмкость INPUT из единожды удерживаемой привязки и
`pendingQuotes`, умноженного на худшую раскладку одиночной публикации, сохраняя
ёмкость строк. Эти ёмкости не означают wire-байты.
[Контракт владения публикацией](PUBLISHER.ru.md#владение-публикацией-и-ёмкость)
уже сохраняет резерв целой публикации после отсоединения и частичного потребления.
Эта гарантия должна пережить снятие квоты строк.

## Принятая политика байтовых бюджетов

Ввод, состояние коллектора, очередь каждого потребителя, удерживаемые пользователем
данные и выходные кадры получают отдельные настраиваемые байтовые бюджеты. Общий
владелец ресурса атомарно выдаёт резервы, исключая повторное обещание одной ёмкости
дочерним владельцам. Учитывается удерживаемая ёмкость payload, контейнеров,
дескрипторов, индексов, строк, схем и метаданных. Общая физическая память
учитывается один раз в физическом домене; квоты способных удержать её потребителей
учитываются независимо. Квота не создаёт ещё одну физическую копию payload
и не делает удержание бесплатным.

Каждому параметру нужны тип, единица в байтах, владелец, значение по умолчанию,
поддержанный диапазон, правило проверки и режим применения. Структурные параметры
проверяются до активации. Запрошенное значение становится действующим после
принятия потребляющим компонентом; неподдержанное значение нельзя показывать
как действующее. Уменьшение ниже занятой ёмкости и живых резервов отклоняется.
Значения по умолчанию и размеры внутренних пулов требуют опубликованного расчёта
ресурсов и измерений; этот контракт не назначает новых числовых пределов или имён
публичного API.

Размер передачи независим от входной ёмкости, размера кадра QTP и пакета генератора.
Готовые данные передаются без ожидания заполнения порции. Бюджет работы в
байтах/времени может остановить текущий шаг progress; оставшиеся принятые данные
сохраняются, а другие участники получают возможность продвигаться. Числа записей
могут оставаться семантическими пределами результата или вспомогательными квантами
планирования. Они не должны задавать общий предел допуска или заменять учёт памяти.

У каждой части состояния один исполнительный владелец изменений. Готовые порции
передаются через очередь при смене владельца исполнения или необходимости изоляции.
Входная очередь целых публикаций остаётся границей нескольких производителей
и одного потребителя. SPSC выбирается только при доказанной соответствующей
топологии. Добавление очередей или выбор lock-free структуры сами по себе
не доказывают улучшения.

## Владение, давление и ошибки

Полный принимаемый объект резервируется до публикации любой его части. Ошибка
резервирования, проверки или выделения памяти не показывает частичной публикации
или частичного желаемого состояния. Конкурирующие производители не должны
резервировать одну свободную ёмкость. Сохраняются существующий барьер допуска/close
и порядок выбранного коллектора. Курсор рабочего потока удерживает полный резерв
INPUT до потребления всех строк или окончательного отбрасывания публикации.

Callback заимствует пакет только на время вызова. Удержанное generic-хранилище
и владеющие типизированные проекции имеют собственное время жизни. Ожидающие,
исполняемые и завершающиеся callback сохраняют выбранные данные и callable до
завершения, включая отмену, отказ executor и окончательное освобождение captures.
Удерживаемый владелец продолжает учитываться после закрытия endpoint; ёмкость
освобождается после уничтожения соответствующего хранилища. Устаревшая задача
executor не должна выбрать повторно использованный слот или удержать старый payload.

Замена обязана различать следующие исходы:

- Объект больше пустого применимого бюджета постоянно превышает предел при этой
  настройке. Ожидание освобождения другого объекта этого не исправит.
- Временно занятая ёмкость может позволить повтор или ожидание освобождения.
  Попытка допуска остаётся атомарной, причина нехватки ёмкости доступна.
- Исчерпание работы останавливает или отклоняет указанную работу; оно не означает
  переполнения памяти, успешной доставки или завершённой команды.
- По умолчанию при исчерпании бюджета очереди потребителя и невозможности сохранить
  следующую запись STREAM завершается с явным gap, а HISTORY сообщает неполноту.
  Медленный потребитель, данные которого ещё помещаются, не вызывает такого отказа.
  TICKER схлопывает только в пределах своего контракта. Пауза общего ввода или явно
  разрешённая потеря — наблюдаемый выбор приложения.
- Удержанная доставка, повторная подписка и reset сохраняют отдельные правила
  владения и завершения. Сброс счётчика не списывает живую память старого поколения
  и не подтверждает недоставленный callback.

Пауза multicast-чтения не создаёт обратного давления на отправителя. Автоматическая
выгрузка переполнения на диск не входит в политику. Байтовые бюджеты ограничивают
описанную модель удерживаемой ёмкости; буферы ОС, стеки и накладные расходы библиотек
и allocator измеряются отдельно. Поэтому бюджеты не задают точный предел RSS процесса.

## Миграция и критерии готовности

Сначала заменяется гарантия хранилища, затем снимается соответствующая проверка
числа. Для каждого затронутого профиля реализация должна:

1. Установить всех владельцев от ввода через коллектор, очередь, callback/удержание
   до вывода, включая отсоединённые и старые поколения. До выделения памяти
   рассчитать пик их сосуществования и размеры представления с проверкой арифметики.
2. Добавить независимую байтовую настройку и атомарные резервы на этих границах
   владения. Различать зарезервированную, занятую и удерживаемую ёмкость и причины
   отказа. Сохранить прежний профиль по числу записей на время квалификации
   байтового профиля; явно документировать действующие настройки.
3. Перевести общий допуск строк на байтовую политику и отдельно обеспечить работу
   источника, маршрутизации, проекции, компоновки кадра и очистки. Сохранить
   продвижение частично потреблённой публикации и частично переданного кадра.
4. Проверить много коротких записей сверх каждого прежнего предела при свободных
   байтах; крупные записи; один объект больше пустого бюджета; временную занятость;
   разные пакеты генератора и неполные кадры. Доказать отказ без частичного допуска,
   точные значения полей, дубликаты и порядок.
5. Проверить вместе медленных и здоровых потребителей; удержание после close;
   конкурентные резервы; ошибку выделения памяти; отмену/отказ/завершение callback;
   повторную подписку и reset с удержанными старыми поколениями. Отдельно проверить
   gap, неполноту, схлопывание и исчерпание работы.
6. Сравнить Quote/STREAM с пакетом генератора 8, разными размерами строк и 1/2/4/8
   клиентами. Измерить полную доставку, p99 каждого клиента, копирование,
   кодирование, конкуренцию и удерживаемую ёмкость. Использовать существующие
   [контракт стенда](../../tools/nettest/benchmark/QUOTE-STREAM.ru.md)
   и [определения метрик](../../tools/nettest/benchmark/METRICS.ru.md).
   Более глубокая очередь может сократить повторы или отложить отказ без роста
   скорости полной доставки; снятие предела числа не обещает ускорения.

До заявления о миграции профиля обязательны применимые регрессионные сборки/тесты
проекта и независимое ревью контракта. Байты протокола, точные значения, отдельные
контракты подписок и прежнее поведение остаются покрыты существующими контрактами.
