# Контракт локальной публикации записей

[English version](RECORD-PUBLICATION.md).

Локальный издатель настраивается с проверенным неизменяемым каталогом и упорядоченными именами исходящих полей. Настройкой владеет endpoint. Публикация указывает одну запись каталога, один контракт коллектора и один точный символ. Для идентификации используем существующее владеющее происхождение `RecordContext`. Копии одного проверенного каталога сохраняют происхождение. Контекст независимо проверенного каталога отклоняется даже при совпадении числового ID записи. Получатели могут независимо назначать свои wire ID.

## Значения и допуск

Публикация передаёт точные типизированные значения в логическом порядке каталога. Сохраняются исходные биты чисел и различие между null и пустым значением. При удалении в индексном HISTORY передаётся знаковый индекс удаления без значений полей. Запись данных HISTORY использует индексную раскладку записи и содержит требуемые индексированные значения. Применимость и поддерживаемые флаги определяются выбранным коллектором и wire-профилем.

Синхронный вызов может заимствовать память символа и значений. До возврата издатель получает во владение все принятые данные для асинхронной работы. Вызывающая сторона может сразу изменить или уничтожить исходные данные. Проверка и резервирование ресурсов предшествуют допуску. Неверный идентификатор каталога, форма записи, метаданные или символ, превышение лимитов, переполнение и закрытый издатель приводят к явному отказу. Отказ в допуске одной записи не затрагивает состояние коллекторов, очереди получателей или спрос.

Для одной записи ограничиваем число полей и объём владеющих данных в байтах, включая символ. Для всей ожидающей работы ограничиваем число записей и объём владеющих данных. Сохраняем учёт до применения или отбрасывания, в том числе после извлечения записи из FIFO. Различаем превышение размера записи, исчерпание очереди и ошибку выделения памяти. Ошибка создания записи или выделения памяти до допуска освобождает резерв и не показывает частичную работу.

Отдельный дескриптор издателя и владеющий контекст записи остаются безопасны после уничтожения endpoint. Публикация и закрытие используют общий барьер допуска. Попытка после закрытия барьера возвращает диагностику закрытия. Допущенная ранее работа может быть отброшена при остановке. См. [контракт издателя](PUBLISHER.ru.md).

Допуск означает, что издатель принял работу на обработку. Коллектор STREAM сохраняет порядок допуска в FIFO, включая вызовы из нескольких потоков. TICKER может схлопывать значения одного ключа. HISTORY применяет свои ограниченные правила индексирования, транзакций и снимков. Доставка, закрытие соединений и давление на очереди регулируются контрактами коллекторов и издателя. Допуск не гарантирует получение записи клиентом. Производители координируют вызовы многострочной транзакции HISTORY по одному ключу.

## Совместимость

Используем существующие коллекторы, фильтры подписчиков и кодирование полей. Для обобщённой локальной публикации не требуется JSON или тип события конкретного поставщика. Сохраняем действующие типизированные перегрузки, их поддерживаемые профили, компактный режим и ретрансляцию источника.

Проверяем точные поля стандартных и пользовательских записей по TCP, включая null и пустые значения, повторные вхождения и порядок STREAM, схлопывание TICKER, снимки HISTORY и знаковое удаление. Проверяем неверный идентификатор, некорректные поля, исчерпание ресурсов и остановку с отказом в допуске.

## Профиль локального каталога

Передайте бинарную схему и упорядоченные исходящие имена через
`PublisherOptions::catalog`. Оставьте `source` пустым и `mixed` равным false.
Endpoint объявляет TICKER, STREAM и HISTORY. Для HISTORY требуется согласованная
опция QTP `hs`. TICKER и STREAM принимают полные записи с метаданными по умолчанию.
Типизированные перегрузки `publish` по-прежнему используют компактный и смешанный профили.

Передайте `RecordContext` из той же схемы, что использована при настройке endpoint,
и по одному `FieldValueView` на логическое поле в порядке каталога.
Память вызывающего кода нужна только на время вызова. Endpoint проверяет исходящее
описание до приёма клиентов. Каждый подписчик может назначать свои ID записей.

Профиль принимает до 128 логических полей и непустой точный символ до 256 единиц
UTF-16. Для поля STRING действует существующий предел wire в 1 024 единицы UTF-16.
Значение `PublisherRecordLimits::rowBytes` по умолчанию составляет 16 КиБ,
`PublisherRecordLimits::pendingBytes` — 256 КиБ. В учёт одной записи входят массив
представлений полей, текст UTF-16 вместе с символом и байты непрозрачных значений.
Постоянные ячейки FIFO и служебные данные аллокатора в этот объём не входят.
Общий параметр `pendingQuotes` ограничивает число допущенных записей, включая
текущую запись рабочего потока до применения. После копирования действуют
отдельный ограниченный буфер источника и существующие лимиты коллектора.
В этом профиле `PublisherStatistics::pendingPublications` учитывает текущую запись
до применения.

### Публикация STREAM с байтовыми лимитами

`PublisherOptions::streamBytes` включает независимые ограничения публикации и
выхода STREAM для локального каталога или смешанного издателя. Для приёма
записей каталога `recordLimits.rowBytes` ограничивает каждую запись, а
`recordLimits.pendingBytes` — суммарный объём удерживаемых записей.
Постоянные ячейки очереди отдельно ограничены параметром `pendingQuotes`.
Вызов с несколькими записями принимается целиком. Неверная запись, нехватка
ресурсов или ошибка выделения памяти приводят к отказу всего вызова.

`targetPayloadBytes` задаёт мягкий порог закодированных полезных данных
STREAM, по умолчанию 8 000 байт. Издатель берёт доступные записи по порядку и
отправляет их без ожидания следующих. Он проверяет порог перед добавлением
следующей полной записи. Одна запись может превысить мягкий порог.
`maxFrameBytes` отдельно ограничивает полный QTP-кадр вместе с префиксом
длины, по умолчанию 65 536 байт. Запись, превышающая жёсткий предел кадра,
вызывает ошибку ресурсов. Границы входного вызова API и исходящего кадра
могут различаться.
В этом профиле `streamBatchRecords` не ограничивает публикацию или выход.
Ячейки очереди и учитываемая память имеют отдельные пределы. Память каждой
записи в очереди клиента учитывается по измеренному размеру выделения. Размер
кадра определяется объёмом целых записей и наличием данных в очереди. При
маленькой входной очереди готовых записей может не хватить до порога. При
ошибке формирования кадра издатель закрывает затронутого клиента и увеличивает
`failedFrames` STREAM.
Если у всех подписанных клиентов исчерпан запас под очередную порцию,
принятые STREAM-записи остаются во входной очереди, пока продолжается отправка.
Клиенты со свободной ёмкостью могут продолжать получать записи.
Действующие ограничения переполнения и таймаута сокета применяются отдельно
к каждому клиенту.

В смешанном типизированном профиле каждая ячейка фиксированного формата
учитывается во входном байтовом бюджете. Для памяти рабочего потока действует
отдельный конечный бюджет.

Без этого профиля `streamBatchRecords` сохраняет прежнее поведение. Используйте
этот режим со старыми получателями, у которых действует низкий предел числа
записей в кадре. В актуальном Feed можно задать ожидаемый максимум тела
QTP-сообщения через `EndpointOptions::maximumReceiveMessageBytes`.
При частичной отправке кадр и его исходные записи удерживаются до завершения.
При изменении спроса сохраняется существующая политика для отозванной записи
в частично отправленном кадре.

### Индексный HISTORY

Каталог должен объявлять поддерживаемую раскладку индекса времени. Подписка и
публикация в HISTORY исключают записи с более чем 128 логическими полями и
раскладки, где имя первого исходящего поля с типом, отличным от VOID, начинается
с `Event`. Кодировщик QTP не может передать удаление в такой раскладке, включая
удаления, которые коллектор формирует на границах снимка. Такие записи доступны
в TICKER и STREAM в пределах их обычных ограничений.

Для обычного обновления вызывайте `publishRecord` с четырьмя аргументами. Для
индексных управляющих флагов передайте `PublisherHistoryMetadata` пятым аргументом.
Поддерживаются `TX_PENDING`, `REMOVE_EVENT`, `SNAPSHOT_BEGIN`, `SNAPSHOT_END`,
`SNAPSHOT_SNIP` и `SNAPSHOT_MODE` из `events::indexed_event_flags`. Обычная запись
содержит все логические поля, а её индекс определяется раскладкой каталога.
Значение `INT64_MAX` зарезервировано для виртуальной границы снимка. Издатель
отклоняет обычные записи с этим индексом. Для удаления установите `REMOVE_EVENT`,
передайте пустой список полей и точный знаковый 64-битный `removalIndex`. Индекс
сохраняется независимо от того, сколько его битов представлено в раскладке
данных. Издатель проверяет согласованность этих метаданных до допуска.

Например, передайте полную запись с `SNAPSHOT_BEGIN`, затем завершите снимок
пустым удалением на нижней границе с флагами `SNAPSHOT_END | REMOVE_EVENT`.
Последующие обновления могут передавать `TX_PENDING` до записи, которая снимает
этот флаг. Действующий коллектор HISTORY применяет эти флаги для диапазона
каждой подписки и может формировать удаления на границах снимка.
См. [контракт коллектора HISTORY](HISTORY-COLLECTOR.ru.md).
