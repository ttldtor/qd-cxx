# Совместимость C++ writer с production parser

[English version](INTEROP.md). Английская версия нормативна.

`Verify-Writer.cmake` проверяет tape, созданные нативным writer, через production `FileReader`
закреплённой Java QD. Сравнивается наблюдаемая проекция `STREAM_DATA`: точные имена записей,
порядок полей, исходные скалярные значения, nullable UTF-16 units, символы, flags и cursor sequence.
Fanout RAW callbacks учитывается отдельно и не умножает ожидаемые wire-записи.
Сравнение семантическое: побайтовое совпадение с выводом Java не требуется.

## Входы и запуск

Нативный `qdcxx_tape_writer_tests` принимает каталог контрактных fixtures и
`--emit-dir PATH`. Используйте новый каталог вывода. Каждый случай содержит `tape.qtp`,
`schema.tsv` и `expected.tsv`. Случаи стандартных Quote и Profile также содержат
`schema-mode.txt` со значением `standard`, выбирающим неизменённую production `DXFeedScheme`.
Каждое целочисленное поле, кроме VOID, и каждое объектное поле стандартной схемы должно быть
представлено ровно один раз. Остальные случаи используют явную диагностическую схему без
неявных преобразований.

Оба TSV имеют шесть колонок, разделённых табуляцией, без заголовка. Имена и строки задаются
точными UTF-16 hex в нижнем регистре; `-` обозначает пустую строку, `null` — null значения поля.

| Файл / строка | Колонки |
|---|---|
| schema / record | `record`, имя записи, `-`, `-`, `-`, `-` |
| schema / field | `field`, имя записи, локальный логический ID, локальное имя поля, wire-имя поля, полный ID типа |
| expected / record | `record`, индекс записи, имя записи, символ, flags, Java cursor sequence |
| expected / value | `value`, индекс записи, локальный логический ID, полный ID типа, исходный скаляр, units или `null` |

Из корня репозитория передайте явные пути подготовленного provider и фактического producer binary:

```powershell
cmake '-DJAVA_HOME=C:/path/to/jdk8' '-DUPSTREAM=C:/path/to/locked-QD' '-DRECEIPT=C:/path/to/classpath-receipt.json' '-DINPUT=C:/path/to/emitted-cases' '-DPRODUCER=C:/path/to/qdcxx_tape_writer_tests.exe' '-DRUN=C:/path/to/fresh-verification' -P tools/upstream/tape-write-oracle/Verify-Writer.cmake
```

Receipt создаётся [процедурой подготовки provider](README.ru.md). Каталог запуска не должен
существовать. Прежние captures и ожидаемые результаты не переписываются. JDK форматтера остаётся
отдельным от oracle JDK 8; соблюдайте [инструкции форматирования Java](../../format/README.ru.md).

## Ограничения и доказательства

Harness ограничивает каждый входной файл 16 MiB, записи схемы — 256, поля — 2048,
каждое декодированное имя/строку — 1 048 576 UTF-16 units, записи callbacks — 8192, строки вывода — 131072.
Launcher допускает 1–64 случая, отводит каждому запуску компилятора/parser 30 секунд и задаёт
Java heap 256 MiB. Эти диагностические ограничения не заменяют явные бюджеты нативного writer.

Успешный запуск сохраняет наблюдаемые строки, отдельные stdout/stderr, границы фаз в UTC,
хеши классов provider, входов, инструментов, нативных исходников и producer. Проверяется
неизменность входных байтов, снимка нативных исходников, producer binary и классов provider
за время проверки. Хеш producer идентифицирует переданный артефакт; вызывающая сторона должна
собрать его из соответствующего снимка исходников до создания случаев. Сам хеш не доказывает
такую связь со сборкой.

Нативный исходящий контракт отклоняет sender ID `INT32_MAX`: в закреплённом Java parser
вычисление `id + 1` переполняется при увеличении плотного record map. Меньшие большие ID всё
равно зависят от ограничений массивов и heap Java. Нативные sparse boundary tests не доказывают
успешного production Java parsing на этих ресурсных границах. См. [контракт writer](../../../spec/protocol/TAPE-WRITER.ru.md).
