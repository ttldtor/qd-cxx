# NetTest уровня записей

[English version](README.md).

`qdcxx-nettest` выполняет конечный прогон синтетической нагрузки QTP для одной
физической записи из пакета схемы binary-v2. Источник слушает обычный TCP,
потребитель открывает исходящие TCP-соединения.

Соберите утилиту с транспортом TCP и нативным загрузчиком JSON. Передайте
каталог с двумя файлами `schema.json` и `provenance.json` из одного
[экспорта](../schema-export/README.ru.md). Установленный пакет может содержать
каталоги default и dxlink в `share/qdcxx/schemas`. Утилита читает их до
открытия сокетов. Предел размера схемы составляет 1 МиБ, provenance — 4 МиБ.

```sh
qdcxx-nettest p --bundle /path/to/default --port 7301 --duration 10 --rate 1000 --batch 10
qdcxx-nettest c --bundle /path/to/default --port 7301 --duration 9 --qd-text
```

Источник выводит фактический порт в строке `PORT NUMBER`. Порт 0 позволяет ОС
его выбрать, потребителю нужен ненулевой порт. По умолчанию используются
IPv4 loopback, физическая запись `TimeAndSale`, контракт STREAM и символ IBM.
`--address` принимает числовой IPv4 или IPv6. `--record` и `--symbol`
принимают точные имена в UTF-8. Повторите `--symbol` для циклического
распределения нагрузки по максимум 64 символам, до 256 кодовых единиц UTF-16
в каждом. Источник передаёт клиенту только запрошенные символы. `--instances`
ограничивает число одновременных клиентов источника либо задаёт число
одновременных соединений потребителя.

`--rate` задаёт предложенную нагрузку в записях в секунду на каждого клиента
источника. `--batch` ограничивает число записей DATA в кадре с учётом раскладки.
Задайте `--batch 32` или меньше при работе через ретранслятор с таким пределом.
`--startup` ограничивает запуск отдельно от окна `--duration`. Источник
начинает отсчёт с первого подходящего спроса, потребитель — после завершения
локальной отправки ADD всех соединений. По окончании окна источник даёт до
двух секунд на отправку уже собранных DATA. Приём байтов сокетом не подтверждает
доставку на другую сторону.

Укажите `--contract ticker`, `--contract stream` или `--contract history` с обеих
сторон. Для сравнения отдельных вхождений с QD NetTest используйте STREAM.
HISTORY принимает индексную запись и знаковую сырую нижнюю границу
`--history-bound` потребителя, по умолчанию 0. Источник сопоставляет границу с
экспортированными индексными позициями. При согласованном `hs` первая
подходящая запись отмечается как однострочный снимок; источник не хранит историю.
Синтетические числовые и текстовые значения сохраняют точные типы wire,
для сериализованных Java-объектов используется null.

`RESULT` отдельно сообщает число сгенерированных записей, число записей в
собранных DATA, число записей в полностью отправленных DATA, число проверенных
вхождений на wire на стороне потребителя и число доставленных выбранных
записей. Байты источника включают согласование и завершение отправки, байты и
записи потребителя учитываются в измерительном окне. Неприменимые счётчики равны
нулю. `connections` у источника считает принятые сокеты за время запуска,
у потребителя — установленные. `rps` использует число отправленных записей
источника или доставленных записей потребителя. `--qd-text` дополняет отчёт
сводкой в форме `data … rps` и указывает, что lag недоступен. Определения lag
производителя и потребителя Java различаются. [Сравнение NetTest](../../docs/NETTEST-REFERENCE.ru.md)

## Проверка с Java QD

Запустите `Test-Loopback.ps1` через PowerShell 7, передав собранную утилиту и
схему default. Скрипт создаёт новый каталог журналов и запускает отдельные
нативные процессы для трёх контрактов. Для дополнительной проверки обоих
направлений с Java передайте JDK 8 и classpath сборки закреплённого QD 3.355.
Java NetTest работает до внешней остановки; скрипт завершает собственный процесс
Java после конечного прогона нативной стороны.

```powershell
pwsh -NoProfile -File tools/nettest/Test-Loopback.ps1 -Program $nettest -Bundle $defaultBundle `
  -Java $java -Classpath $qd355Classpath -OutputDirectory $newLogDirectory
```

Общий для Java и C++ сценарий использует STREAM, одно соединение, запись
`TimeAndSale`, синтетический IPF с IBM и пакет размером 10. Java-потребитель
сообщает наблюдаемую скорость, C++-источник считает записи в отправленных
локальному сокету кадрах. Полный каталог отдельно проверяет
[сравнение байтов при экспорте схем](../schema-export/README.ru.md).

## Измерение доставки STREAM со сверкой записей

`benchmark/Measure-Stream.ps1` запускает Record NetTest как источник и
Java QD 3.357 как потребителя записей на IPv4 loopback. Нужны сборка Release,
[classpath QD 3.357](https://github.com/devexperts/QD/tree/qd-qds-3.357)
с `qds.jar`, `dxlib.jar` и `dxfeed-api.jar`, а также JDK, где `javac`
находится рядом с `java`. Скрипт отключает фабрику endpoint с мониторингом
и использует обычный STREAM collector.

```powershell
pwsh -NoProfile -File tools/nettest/benchmark/Measure-Stream.ps1 -Program $nettest `
  -Bundle $defaultBundle -Java $java -Classpath $qd357Classpath -OutputDirectory $newLogDirectory
```

Сценарий использует одну подписку `TimeAndSale` STREAM на IBM. По умолчанию
окно длится десять секунд, предлагаемая скорость — 1 000 записей/с, размер
пакета — одна запись. Потребитель сверяет физическую запись и последовательность
генератора. Прогон успешен, если числа сгенерированных, собранных, полностью
отправленных и независимо полученных записей совпали и ошибок сверки нет.
Объём нагрузки должен укладываться в 22-битный диапазон, чтобы каждая
запись имела уникальный номер последовательности.

`result.json` содержит счётчики, отношение доставленных с учётом drain записей
к окну источника, квантили задержки и сводку CPU и памяти по процессам.
`process-samples.csv` содержит сырые периодические замеры. Задержка измеряется
как знаковая разность часов одной машины между меткой в сгенерированной записи
и чтением записи потребителем. Значение включает декодирование и доставку в
QD, разрешение метки — одна миллисекунда. CPU считается по
разности первого и последнего замеров активного процесса. Пики памяти относятся
к снятым замерам working set и private bytes. В Windows private bytes отражает
приватную выделенную память, а working set — резидентные страницы. Отчёт
показывает CPU и память отдельно для Record NetTest и QD-потребителя.

Справка стенда `-Help` и `-HelpRu` доступна без запуска прогона.

### Запуск источника событий

Соберите `qdcxx_event_nettest` с включённым публичным Feed API. Утилита
`qdcxx-event-nettest` использует встроенный смешанный профиль publisher и
передаёт один `TimeAndSale` на вызов `Publisher::publish()`. Java-потребитель
сверяет последовательность и десять общих полей в обоих режимах. Встроенный
профиль событий также передаёт долю миллисекунды в `TimeNanoPart`.
Схемы на проводе различаются.

```powershell
pwsh -NoProfile -File tools/nettest/benchmark/Measure-Stream.ps1 -Program $eventNettest `
  -ProducerKind Event -Java $java -Classpath $qd357Classpath -OutputDirectory $newLogDirectory
```

Режим Event использует пакет из одной записи и встроенную схему. Источник ждёт
точную подписку, сообщает число принятых к публикации событий и наблюдения
завершения из публичного publisher. Счётчик `drainMs` измеряет опустошение
очереди после последнего приёма события. Java-потребитель сверяет доставленные
записи с числом принятых событий. В режиме Record сверка идёт по числу полностью
отправленных записей. При сравнении одной публикации на вызов задайте
`-Batch 1` в обоих прогонах.

Когда очередь publisher заполнена, источник событий повторяет публикацию
того же события с исходной меткой времени до конечного дедлайна завершения.
После закрытия измеряемого окна новые события не создаются. Отчёт показывает
число повторных попыток и разницу между номинальной нагрузкой и завершёнными
публикациями отдельно от сверки доставки.

Укажите `-Clients 2`, `-Clients 4` или `-Clients 8` для запуска отдельных
потребителей Java QD. Пробная запись с нулевой последовательностью подтверждает
каждую подписку до начала замера. STREAM сверяет точную последовательность и
число записей у каждого потребителя. Параметр `-Contract ticker` включает
`Quote/TICKER`. В этом режиме проверяются возрастание принятой последовательности,
поля и доставка последней принятой версии всем потребителям. Отчёт показывает
количество полученных промежуточных обновлений.
Проверяющий код выполняет приём и чтение TICKER под общей блокировкой:
курсор Java-коллектора ссылается на изменяемое хранилище записи. Измеренная
задержка TICKER включает эту синхронизацию.

Режим Event по умолчанию передаёт метку времени с полем `TimeNanoPart`.
В отчёте приводится знаковый возраст записи в наносекундах. Шаг гистограммы в
центральном диапазоне составляет 1 мкс. Точность часов зависит от системы.
Режим Record использует миллисекундные метки. Отчёт для нескольких потребителей
показывает задержку, CPU и память по процессам, а также отдельно скорость
источника и суммарную скорость доставки.

[Бандл NetTest для Windows](benchmark/windows/README.ru.md) запускает серии
замеров, сохраняет статистику по процессам и содержит отдельную проверку
пропускной способности физического канала.

[Синтетический корпус всплесков](benchmark/burst/README.ru.md) содержит
воспроизводимые данные и предварительно рассчитанный график выпуска.

Пределы, значения по умолчанию и коды завершения `qdcxx-nettest` приведены в `--help` и
`--help-ru`. Справка не читает схемы и не запускает сетевую подсистему.
