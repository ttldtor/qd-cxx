# Единицы и границы измерений NetTest

[English version](METRICS.md).

Эти определения применяются при сравнении издателей записей, публичного API
событий и реализаций на Java или .NET. В результате указываются нагрузка, точка
наблюдения и интервал измерения. Вместе со скоростью сохраняются исходные
счётчики, чтобы читатель мог повторить расчёт.

Ниже задан контракт сравнения. Последний раздел связывает его с существующими
утилитами и перечисляет наблюдения, которые они пока не предоставляют. Имена
полей существующих отчётов и сетевые форматы сохраняются.

## Количество и скорость

Исходная запись — одно созданное обновление до раздачи клиентам. Доставка —
одно обновление, наблюдаемое одним клиентом. При сравнении API событий с записями
указывается отображение событий в записи: одному событию может соответствовать
несколько записей. Записи, события, кадры QTP и байты считаются отдельно.

| Наблюдение | Что считаем | Момент завершения |
| --- | --- | --- |
| Предъявлено | Различные обновления, переданные API публикации | Первая попытка передачи; повторные попытки сохраняют идентичность обновления |
| Принято | Обновления, за которые издатель принял ответственность | Успешный приём; для асинхронного API указывается подтверждающая его операция завершения |
| Закодировано | Вхождения записей в готовые кадры DATA | Успешное формирование кадра до записи в сокет |
| Записано в транспорт | Вхождения записей в полностью записанные кадры DATA | Локальный транспорт принял все байты кадра |
| Доставлено | Обновления, наблюдаемые в указанной точке приёмника | Проверяющий код или обработчик приложения просмотрел обновление |

Заданная скорость определяет желаемую интенсивность нагрузки в исходных
записях/с. Для профиля без ограничения темпа со значением скорости ноль
показываются фактические скорости предъявления и приёма. Ноль в этом профиле
обозначает отсутствие регулирования темпа.

Для каждой измеренной скорости сохраняются количество, моменты начала и конца,
длительность в наносекундах и признаки включения запуска или завершения очередей.
Формула: `скорость = количество * 1 000 000 000 / длительностьНс`, без целочисленного
усечения. При отсутствующей или неположительной длительности скорость недоступна.
Даже при округлении вывода сохраняется измеренная длительность. Заданная и
фактическая длительности записываются раздельно.

Показываются скорость источника и скорость доставки каждому клиенту. Суммарная
скорость доставки вычисляется по сумме доставок за один общий интервал. Если
интервалы клиентов различаются, каждый указывается отдельно: сумма их скоростей
не описывает единый измеренный интервал. При кодировании и записи может считаться
отдельное вхождение для каждого получателя. Совместное использование готового
кадра позволяет учесть его однократно для нескольких получателей. Применённое
правило указывается явно.

Нужно указать, что охватывает таймер: передачу в API, завершение сетевой записи
или последнее наблюдение приёмника. Число доставок с учётом завершения очередей,
делённое на интервал генератора, — скорость, нормированная на интервал генератора.
Сквозная скорость завершения использует интервал от генерации первой измеряемой
записи до последней проверенной доставки. Подтверждение или выход процесса могут
задавать более позднюю границу завершения; её нужно указать, если время самого
наблюдения приёмника недоступно.

Например, источник принял 1 000 записей за секунду, а два клиента получили их за
1,2 секунды от начала генерации. Скорость источника — 1 000 записей/с, каждого
клиента — примерно 833,33 доставки/с, суммарная — 1 666,67 доставки/с за интервал
1,2 секунды. Деление 2 000 доставок на секундный интервал генератора даёт
2 000 доставок/с, нормированных на этот интервал. У этих расчётов разные знаменатели.

## Корректность и пропускная способность

Проверки готовности подписок и прогрев исключаются из всех измеряемых счётчиков;
их количества сохраняются отдельно. Прогон STREAM пригоден для сравнения точной
доставки после проверки количества, порядка, полей и конечного состояния у
каждого клиента, включая доставки при завершении очередей. Дубликаты, пропуски,
повреждённые записи, отказы в приёме, оставленные обновления и истечение времени
завершения указываются явно. Успешно повторённое обновление учитывается один раз
как предъявленное и один раз как принятое.

TICKER может объединять промежуточные обновления. Для него показываются принятые
и наблюдаемые поколения, а также последнее поколение по каждому ключу.
Применяются правила порядка и конечного состояния коллектора TICKER; число
наблюдаемых обновлений имеет иной смысл, чем число точных доставок STREAM.
Для сравнения количества записей HISTORY также нужны заданные правила снимков,
транзакций и хранения.

Максимальную устойчивую скорость можно заявить после прогонов с возрастающей
нагрузкой, сверкой доставки и измерением незавершённой работы в начале и конце
интервала. Допустимый объём этой работы и критерии задержки указываются явно.
Конечный прогон с последующим опустошением очередей подтверждает завершённую
доставку при заданной нагрузке. Если рост очередей не измерялся, устойчивость
скорости остаётся неподтверждённой. В отчёт входят максимальная проверенная
нагрузка, прошедшая критерии, и первая не прошедшая, если она наблюдалась.

Внутри сравнения сохраняются схема, значения данных, темп генерации, размер
порции генератора, число клиентов, байтовые настройки очередей и кадров,
транспорт, параметры среды исполнения и сборка приёмника. Порядок запуска
реализаций чередуется; результаты отдельных прогонов сохраняются. Указываются
топология CPU, настройка часов и фоновая нагрузка. Результат виртуальной сети
содержит её описание; пропускная способность физического канала измеряется
отдельным прогоном на таком канале.

## Задержки и часы

Для каждой временной отметки задаётся точка наблюдения. Возраст от генерации
до приёма измеряется по отметке, установленной один раз при создании обновления
и сохранённой при повторных попытках публикации. В него входит ожидание приёма
издателем. Для измерения от приёма издателем до получения клиентом нужна
отдельная отметка успешного приёма.

Локальные интервалы измеряются монотонными часами. Для задержек между процессами
нужно подтвердить общие начало отсчёта, единицу и преобразование часов. Для
односторонней задержки между машинами дополнительно указываются способ
синхронизации и погрешность. Наносекундная единица API языка сама по себе не
подтверждает совместимость или точность часов. Коррекция календарных часов может
дать отрицательный возраст. Такие значения и их количество сохраняются; перед
ранжированием реализаций проверяется связь часов.

Результат содержит число отсчётов, минимум, максимум, правило ранга процентиля,
диапазон гистограммы и ширину интервалов. Сохраняются количества отсчётов вне
диапазона; процентиль недоступен, если его ранг попал за пределы представленного
диапазона. Процентили считаются для каждого клиента. Максимальный из p99 клиентов
называется худшим клиентским p99. Общий процентиль требует объединения совместимых
гистограмм или исходных отсчётов. Усреднение клиентских процентилей контрактом
не определено.

Текущий Java `StreamReceiver` использует ранг `ceil(N * p / 100)` для целых
процентилей. Его p50, p95 и p99 равны **нижней границе** интервала гистограммы,
в который попал этот ранг:

| Диапазон возраста | Ширина интервала |
| --- | --- |
| От -1 с до значений меньше -10 мс | 1 мс |
| От -10 мс до значений меньше 100 мс | 1 микросекунда |
| От 100 мс до 30 с включительно | 1 мс; для 30 с есть конечный интервал |

Значение p99, равное 12 345 000 нс в центральной области, помещает представленный
квантиль в диапазон `[12 345 000, 12 346 000)` нс. Верхняя граница 12 345 000 нс
этим результатом не подтверждается. Миллисекундные поля используют округление
вниз, включая отрицательные значения. Наносекундные минимум и максимум сохраняют
фактические крайние отсчёты, в том числе за пределами гистограммы. При отсутствии
отсчётов процентили недоступны. Текущий приёмник не выдаёт p99.9.

TimeAndSale использует календарные отметки; наносекундный режим включает
`TimeNanoPart`. Синтетический Quote/STREAM кодирует общие монотонные часы с
микросекундной точностью в полях Quote. Единица результата `ns` не повышает
точность этого кодирования. Перед сравнением возраста Quote нужно проверить
общие часы выбранных сред C++, Java и .NET на машине измерения.

## CPU и память

Для CPU указываются процесс или поток, приращения пользовательского и системного
времени CPU и календарный интервал между теми же двумя отсчётами.
`averageCpuCores = (userCpuSeconds + systemCpuSeconds) / elapsedSeconds`.
Один полностью занятый логический процессор даёт 1,0 среднего занятого ядра,
или 100% по шкале одного ядра. Доля доступной мощности машины равна
`100 * averageCpuCores / availableLogicalProcessors`; сохраняются делитель,
привязка к процессорам и действующие квоты. Две секунды CPU за одну секунду
измерения дают 2,0 ядра, 200% по шкале одного ядра и 25% восьми доступных логических
процессоров. Среднее число ядер не показывает загрузку отдельных потоков или
затраты CPU на копирование и кодирование: для этого нужна атрибуция по потокам.

Измерения памяти сопровождаются названием API платформы и периодом опроса:

- Рабочий или резидентный набор — резидентные страницы процесса на момент отсчёта.
- Частные байты — показатель частной памяти платформы, с собственным названием.
- Пик по отсчётам — максимальное наблюдение за указанный интервал; всплески между
  отсчётами могут быть пропущены.
- Пик ОС — счётчик операционной системы с указанием области накопления и сброса.
- Память в конце — последнее наблюдение на указанной границе, например после
  опустошения очередей у ещё работающего процесса. Время фиксируется до его выхода.

Эти показатели хранятся отдельно друг от друга, от резервов аллокатора и от
полезных байтов очередей. Сумма индивидуальных пиков процессов складывает
максимумы, которые могли наблюдаться в разное время. Для одновременного суммарного
пика нужны согласованные по времени отсчёты. Неподдерживаемый показатель
помечается недоступным с указанием причины.

## Наблюдения существующих утилит

Таблица описывает реализацию в репозитории. Отсутствующие наблюдения остаются
недоступными до появления соответствующих измерений.

| Утилита или поле | Значение и границы |
| --- | --- |
| Record NetTest `generated`, `composed`, `written` | Созданные физические строки, строки успешно сформированных кадров DATA и строки полностью записанных кадров DATA. Генерация отдельная для каждого соединения; сумма содержит вхождения для получателей. Отдельного счётчика приёма публичным издателем в этом пути нет. |
| Record NetTest, поля издателя `seconds`, `rps` | `seconds` — заданное время генерации. `rps` целочисленно усекает `written / seconds` и может учитывать запись при завершении очередей. Для сравнения нужно пересчитать подписанную скорость из исходных полей. |
| Event NetTest `generated`, `admitted` | Созданные исходные события и успешно принятые события; повторы считаются отдельно. В синтетическом TimeAndSale одно событие соответствует одной записи. |
| Event NetTest `ingressRecords`, `sentFrames`, `drainMs` | Вход в коллектор издателя, полностью отправленные кадры и длительность локального завершения очередей. Они не подтверждают доставку приёмнику или количество записей в кадре без дополнительных наблюдений. Из первых двух полей исключены стартовые проверки подписки. |
| Event NetTest `seconds` | Заданный интервал генерации. Оставшиеся попытки приёма и завершение очередей могут продлить работу за его пределы. |
| Издатель Quote `publishNs`; издатель Java `elapsedNs` | Измеренное локальное время цикла передачи в API. Завершение приёмника проверяется отдельно. Эти скорости сравниваются как приём или передача в API с учётом контракта каждого API. |
| `Measure-Stream.ps1`: `offeredRps`, `nominalRecords` | Заданные интенсивность и количество. Фактическое число различных предъявленных обновлений не выдаётся. |
| `sourceRecordsPerSecond` | В режиме Record используются полностью записанные вхождения; в Event — принятые исходные события. Оба значения делятся на `seconds` издателя. Границы завершения у них различаются. |
| `deliveredIncludingDrainPerProducerSecond` | Сумма проверенных доставок клиентам, включая завершение очередей, делённая на `seconds` издателя. Время завершения приёмников в знаменатель не входит. |
| CPU из `Measure-Stream.ps1` | Приращения пользовательского и системного CPU между первым и последним активными отсчётами; `averageCpuCores` использует этот интервал. Активные интервалы процессов могут различаться. |
| Память из `Measure-Stream.ps1` | Первый и медианный рабочий набор, пик рабочего набора и частных байтов по отсчётам. Номинальный период — 100 мс, с погрешностью планирования. Память в конце и пик ОС не выдаются. |

Существующее сравнение .NET использует тот же приёмник и синтетические поля Quote.
Для каждого прогона указываются точные версии SDK и нативной среды, границы таймера
публикации и успешного приёма применённого издателя. Сопровождаемого издателя .NET
в этом каталоге репозитория нет; значения его метрик нельзя выводить из имён
полей Java или C++.

## Состав результата

Сравнимый результат сохраняет описание нагрузки, версии и настройки сборки;
заданную и наблюдаемую интенсивность; счётчики и интервалы по границам; вывод
проверки доставки и гистограмму каждого клиента; отсчёты CPU и памяти процессов;
учёт проверок подписки, прогрева и завершения очередей; недоступные наблюдения
с причинами. Команды находятся в
[описании раздачи нескольким клиентам](FANOUT.ru.md) и
[описании Quote/STREAM](QUOTE-STREAM.ru.md). Сам контракт результатов
производительности не добавляет.
