# Проверка нагрузки на уровне записей

[English version](RECORD-WORKLOAD.md).

Проверка использует физическую запись `TimeAndSale`, контракт STREAM и стандартную схему binary-v2. Каждый прогон использует одно соединение с источником и не более 10 записей в одном DATA-кадре. Для прямых прогонов NetTest задано 100 записей в секунду, для ретранслятора с фильтрами — 100 и 250 записей в секунду. Это конечные функциональные прогоны.

## Совместимость NetTest

QD 3.355 NetTest и qd-cxx NetTest соединялись напрямую в обоих направлениях. Java выбирает `TimeAndSale` свойством `com.devexperts.qd.tools.NetTest.record`, размер batch задаётся `com.devexperts.qd.tools.NetTest.batchSize=10`. Обе стороны подписываются на `IBM`. Профиль полного каталога ретранслятора требует от источника все три контракта QTP, а экземпляр NetTest объявляет выбранный контракт. Ретранслятор и фильтры проверялись отдельным сценарием ниже.

Руководство NetTest описывает экспорт схемы, сборку, параметры и команду прямой проверки с Java. Java-источник записей закреплён на QD 3.355. [Руководство Record NetTest](../tools/nettest/README.ru.md), [источник записей QD 3.355](https://github.com/devexperts/QD/blob/0ddc0a09779fb61d74cc0b37c6449ff47dcb715f/qd-tools/src/main/java/com/devexperts/qd/tools/NetTestProducerDistributorThread.java)

| Сборка и направление | Наблюдение потребителя | Наблюдение источника |
|---|---|---|
| Windows MSVC Release, Java → C++ | 590 записей за 6,00974 с | Java ограничена 100 записями/с |
| Windows MSVC Release, C++ → Java | Java сообщила положительную интервальную скорость | записано 798 DATA-записей за 8 с |
| Windows MSVC Release, C++ → C++ | 598 записей за 6,00162 с | записано 600 DATA-записей за 8 с |
| Linux GCC ASan/UBSan, C++ → C++ | 595 записей за 6,00001 с | записано 595 DATA-записей за 8 с |
| Linux GCC ASan/UBSan, Java → C++ | 350 записей за 6,0008 с | Java ограничена 100 записями/с |
| Linux GCC ASan/UBSan, Java → C++, повтор | 600 записей за 6,00025 с | Java ограничена 100 записями/с |
| Linux GCC ASan/UBSan, C++ → Java | Java сообщила положительную интервальную скорость | записано 799 DATA-записей за 8 с |

Окна источника и потребителя начинаются и заканчиваются независимо. Разность счётчиков поэтому не определяет число потерь. C++ NetTest пока выдаёт число записей и скорость без распределения задержек. Java вычисляет собственный lag по полям записи с миллисекундной точностью исходного времени.

Прогон Java → C++ повторили с побайтово сверенной копией classpath на файловой системе Linux. В первой попытке C++ → Java подходящая подписка не поступила к сроку запуска. Повтор с исходным classpath на подключённой файловой системе прошёл при лимите ожидания в 120 секунд. Отдельный прогон с локальной копией classpath тоже прошёл.

## Фильтрующий ретранслятор и последовательность

Отдельный конечный TCP-источник передаёт записи через ретранслятор полного каталога двум клиентам. Оба запрашивают `IBM` и `MSFT`. Первая политика допускает `TimeAndSale`/`IBM`, вторая — `TimeAndSale`/`MSFT`. Источник отправляет по 250 пронумерованных записей каждого символа и отдельный конечный маркер. Каждый клиент проверяет полную последовательность, символ, дубликаты и порядок. Политики используют одно соединение с источником и одинаковый предел batch.

| Сборка | Суммарная заданная нагрузка | Доставка | p95 от отправки batch до полного кадра |
|---|---:|---|---|
| Windows MSVC Release | 100/с | по 250/250, без пропусков и дублей | 5,45 и 5,46 с |
| Windows MSVC Release | 250/с | по 250/250, без пропусков и дублей | 8,23 и 8,26 с |
| Linux GCC ASan/UBSan | 100/с | по 250/250, без пропусков и дублей | 40,6 и 44,1 мс |
| Linux GCC ASan/UBSan | 250/с | по 250/250, без пропусков и дублей | 89,9 и 93,8 мс |

Задержка измеряется через `monotonic_ns` одного тестового процесса. Отсчёт начинается перед кодированием batch источника и заканчивается после полного чтения кадра потребителем. Все записи batch получают общую начальную метку. Измерение включает сокеты, очередь ретранслятора и планирование. Окна отправки и полной доставки различаются. Windows использует Release, Linux — ASan/UBSan, поэтому таблица не выделяет влияние операционной системы. Причина более длинного измеренного интервала на Windows пока не установлена.

CPU и пиковая резидентная память ретранслятора и тестового процесса измерялись раздельно. Интервалы включают запуск и согласование соединений. Пронумерованный прогон проверяет потери в заданной нагрузке, а временные NetTest прогоны имеют независимые окна измерений.

| Сборка и суммарная нагрузка | Окно проб relay | CPU relay | Пиковая резидентная память relay |
|---|---:|---:|---:|
| Windows Release, 100/с | 11,27 с | 203 мс | 24 969 216 байт |
| Windows Release, 250/с | 11,27 с | 219 мс | 25 014 272 байт |
| Linux ASan/UBSan, 100/с | 6,53 с | 1 690 мс | 221 532 160 байт |
| Linux ASan/UBSan, 250/с | 3,41 с | 1 220 мс | 221 626 368 байт |

Для проверки последовательности используются TCP-источник, ретранслятор и два клиента. Источник поочерёдно отправляет `IBM` и `MSFT`, по 250 записей каждого символа с заданной суммарной скоростью, batch не более 10, затем отдельный конечный маркер каждой последовательности. Политики STREAM задаются как `:TimeAndSale&IBM` и `:TimeAndSale&MSFT`. Оба клиента запрашивают оба символа. Отправку начинают после подтверждения обеих допустимых подписок источником. Каждый клиент проверяет полную последовательность и отсутствие чужого символа. Настройка политик по адресу есть в тестах Publisher. [Тесты фильтров Publisher](../tests/conformance/publisher_tests.cpp)

Во время Linux-прогонов выполнялась другая локальная сборка. Цифры описывают отдельные запуски и не определяют устойчивый предел производительности.
