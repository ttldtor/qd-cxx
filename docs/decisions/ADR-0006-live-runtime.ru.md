# ADR-0006 — Необязательная live-среда выполнения и проверенный TLS-профиль

[English version](ADR-0006-live-runtime.md). Авторитетной является английская версия.

Статус: выбранный вариант проектирования для предстоящих адаптеров; область квалификации зафиксирована ниже.
Это решение не реализует live-транспорт, не подтверждает совместимость с провайдерами и не фиксирует принятие владельцем.

## Контекст и границы

[ADR-0005](ADR-0005-live-subscriptions.ru.md) сохраняет независимость логики подписок/сессий от I/O и возлагает на внешний хост выполнения ответственность за продвижение до quiescence. Следующим адаптерам нужны конкретная зависимость для Windows/Linux, политика отмены и доверия. Отменённая публичная операция не обязательно означает завершение resolver worker; возврат из event loop не означает завершение закрытия.

Выбранное направление реализации: C++23, standalone Asio для executor/TCP, c-ares для асинхронного DNS и необязательный OpenSSL для TLS. Ни одна из этих зависимостей не относится к core, encoding, event mapping или чистой реализации protocol/session. Существующие профили tape и API остаются без изменений.

## Закрепление зависимостей и профиль сборки

Байты выпуска, лицензия и настройки сборки входят в профиль; новый или иначе настроенный SDK не считается подходящим лишь потому, что его API линкуется. Получение зависимостей выполняется явно и локально для проекта; configure не должен незаметно получать сетевые зависимости. Менеджер пакетов и глобальная установка не требуются.

Патч DNS изменяет два upstream-файла; его применение воспроизводит квалифицированное дерево исходников, не меняя исходный архив.

## Владение executor и TCP

Использовать один `asio::io_context` с управлением со стороны вызывающего кода и одним активным потоком-владельцем на хост выполнения. Приложение может запустить владельца в принадлежащем ему потоке. При использовании Asio timer waits Windows IOCP также использует SDK-помощник ожидания таймера: он только пробуждает IOCP, но не вызывает callbacks приложения. Его поток, стек и время жизни учитываются в ресурсах runtime. При остановке контекст пробуждает и присоединяет helper после опустошения операций владельца, вне callbacks. Квалифицированный TCP-адаптер не создаёт timer waits, как уточняется ниже. Это единая область последовательного выполнения callbacks, а не обещание единственного потока в процессе. Для deadlines использовать монотонные часы runtime; чистым компонентам передавать явное время. Публичный API не требует типов Asio/native socket/TLS.

Все операции session, socket, timer и TLS сериализуются на потоке-владельце. Другие потоки отправляют ограниченные команды через control port хоста. Владельцы чтения/записи, состояние операций, контекст и leases эпох живут до завершения всех completion handlers. Одновременно может выполняться одно чтение и одна запись; их состояния независимы, каждый буфер сохраняется до своего завершения.

Остановка из callback запрашивает вывод из эксплуатации и возвращает управление. На потоке-владельце отклонять новые задачи, отменять deadlines, отменять/закрывать принадлежащие сокеты и выводить DNS-канал из эксплуатации. Продолжать обработку всех незавершённых completions до сообщения о завершении закрытия или освобождения эпохи. Успешный completion, пришедший в гонке, всё ещё принадлежит исходной эпохе и не должен публиковаться в замену. Закрытие сокета не отзывает байты, уже принятые ядром, и не означает, что peer подтвердил или применил сообщение.

[`io_context::stop`](https://think-async.com/Asio/asio-1.38.2/doc/asio/reference/io_context/stop.html) прекращает dispatch; это не реализация отмены/дренирования. Ни graceful shutdown TLS, ни блокирующее присоединение хоста/потока нельзя выполнять внутри callback пользователя. Graceful close ограничен deadline, затем следует определённому пути abort без ложного сообщения о сброшенном результате. Блокирующий callback пользователя не входит в гарантию принудительного завершения; см. предварительное условие прогресса хоста в ADR-0005.

## Уточнения квалификации TCP-адаптера

[Контракт TCP-адаптера](../../spec/transport/TCP-RUNTIME.ru.md) выбирает более узкий
путь исполнения для конечных бюджетов работы и retirement. Asio timer waits
не создаются: вызывающая сторона продвигает steady-clock сроки и progress hints.
Описанный выше Windows timer helper остаётся фактом SDK и проверки реализуемости,
а не потоком этого адаптера. После Linux readiness выполняется одна native
receive/send попытка; Windows native nonblocking connect исключает скрытый
select-reactor fallback SDK. Неограниченные user-space EINTR retries не выдаются
за предположение о kernel scheduling.

Текущий runtime требует [c-ares qdcxx2](../../cmake/runtime-profile/README.ru.md).
Кумулятивная поправка сохраняет прежние ограничения конфигурации и исправляет
владение deferred response/передачу ошибки при отказе queue admission. Исходники,
lock и результаты qdcxx1 остаются историческими доказательствами. Полные manifests
связывают все 637 файлов Asio и 532 квалифицированных файла c-ares; одного заголовка
версии для квалификации недостаточно.
[Вывод ресурсов DNS](../../spec/transport/DNS-RESOURCES.ru.md) разделяет SDK storage
reservation, консервативные work credits, allocator overhead, native resources,
RSS и задержку.

## DNS и инициализация процесса

Для этого профиля не использовать `asio::ip::tcp::resolver`. В закреплённой реализации отмена сбрасывает token, а `socket_ops::background_getaddrinfo` проверяет его до входа в блокирующий `getaddrinfo`; остановка пула resolver присоединяет его worker. Это свидетельство по исходному коду, а не измеренный тайм-аут системного lookup.

Использовать канал c-ares с управлением со стороны вызывающего кода, без `ARES_OPT_EVENT_THREAD`. Вывод event thread из эксплуатации может присоединить работу системной конфигурации, вновь создав ожидание системной операции при закрытии. Подготавливать канал на явной границе конфигурации до активации и держать его в пределах времени жизни resolver внешнего хоста для одного upstream run/независимой области вывода из эксплуатации на протяжении эпох соединений этого run. `ares_cancel` отменяет весь канал: нельзя делить отменяемый канал между независимыми run. Новые запросы получают новые идентификаторы эпохи/операции. Во время активной работы не запускать фоновый монитор конфигурации или периодический `ares_reinit`.

Пока запрос ожидает ответа, монотонные deadline ticks владельца выполняют ограниченные снимки fd, проверку готовности с нулевым тайм-аутом и продвижение c-ares. Второго владельца дескрипторов и потока опроса DNS нет. C callbacks на том же владельце сохраняют ограниченные результаты без исключений; они не вызывают код приложения и не уничтожают канал. Учитывать сокеты, состояние запросов/ответов/кэша и одновременно старое и выводимое из эксплуатации владение, включая состояние SDK. Отключить кэширование запросов и сортировку адресов. Использовать socket-function callbacks на канал, чтобы применять общие квоты на байты, датаграммы и системные вызовы за проход; при исчерпании возвращать WOULD_BLOCK без очередного native read. Сохранять неполные TCP-кадры и целые UDP-датаграммы. Учитывать свободную ёмкость входных буферов SDK, рост степенями двойки и одновременное выделение старого и нового буфера, а не только принятые байты. Квалификация адаптера должна обеспечивать конечные пределы fd/ответов/хранилища и работы за проход; считать непрозрачный вызов SDK ограниченным объёмом работы недостаточно. На канал допускается не более одного незавершённого wire query; IPv4 и IPv6 разрешать последовательно, а не выбирать `AF_UNSPEC`; из C callback новый запрос не отправлять.

[Квалифицированный DNS-профиль](../../tests/conformance/transport/runtime-feasibility/dns/profile.json) фиксирует проверенные пределы и консервативную границу входного буфера/перевыделения. Та проверка реализуемости не устанавливала полный SDK heap. Последующий [production-вывод DNS](../../spec/transport/DNS-RESOURCES.ru.md) задаёт консервативную границу requested storage, которую соблюдает TCP-адаптер. Физические накладные расходы аллокатора и RSS остаются вне этой границы.

**Инициализация приложения — предварительное условие поддерживаемого профиля.** Документированный контракт [`ares_library_init`](https://c-ares.org/docs/ares_library_init.html) требует инициализации в главном потоке до активации других потоков. Соответствующий [`cleanup`](https://c-ares.org/docs/ares_library_cleanup.html) выполняется после завершения остальных потоков. Использовать явное время жизни bootstrap, принадлежащего приложению, стандартные аллокаторы и согласованный подсчёт ссылок со всеми прочими пользователями c-ares в процессе. Деструктор клиента/эпохи не должен выполнять глобальную очистку. Позднее первое использование в уже многопоточном приложении без такого bootstrap не поддерживается; сериализация только конструкторов этой библиотеки не выполняет upstream-предусловие.

Стандартная сборка c-ares читает системную конфигурацию, окружение и NSS даже при переопределении явными значениями; чтение некоторых временных файлов не ограничено лимитами приложения. Резервный search, полученный из hostname, — ещё один неявный вход. Предварительная активация не позволяет вынести эти выделения за бюджет. Поэтому квалифицированный SDK отключает эти пути и требует до инициализации конечный явный список числовых IPv4 DNS-серверов. IPv4 nameserver может разрешать адреса peers как IPv4, так и IPv6. Пустая конфигурация серверов завершается ошибкой, а не переходом на localhost. Хранить отдельно upstream-закрепление и точный квалифицированный патч; не обозначать изменённый SDK как неизменённый upstream-выпуск.

Использовать только DNS lookup (`lookups="b"`), `NOSEARCH` и `NOALIASES`; числовые literal endpoints обходят DNS. Автоматическое обнаружение DNS ОС, hosts/NSS/search-domain, переменные среды resolver и автоматическое обновление серверов не выбраны. Приложения передают проверенные конечные настройки; автоматический системный provider потребовал бы собственной ограниченной реализации и квалификации. Не изменять окружение процесса для принудительной изоляции. Переконфигурация требует quiescence и новой явной границы конфигурации; повторные запросы всё равно разрешают актуальные записи через выбранные серверы. Отмена и вывод из эксплуатации должны учитывать DNS-пути UDP и TCP. Callbacks отмены могут выполниться inline на отменяющем владельце; доставку приложению отложить до возврата из вызова C.

Штатный криптографический генератор случайности ОС должен быть доступен и инициализирован:
в квалифицированной Linux-сборке используется `arc4random_buf`, в Windows — `RtlGenRandom`.
Неподдержанные fallback-пути entropy/file/RC4 не квалифицированы. До SDK ownership bootstrap
один раз обращается к выбранному штатному сервису. В Windows FALSE от
[`RtlGenRandom`](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/nf-ntsecapi-rtlgenrandom)
должен давать типизированный bootstrap failure без очистки чужого SDK state.
У Linux [`arc4random_buf`](https://sourceware.org/glibc/manual/latest/html_node/High-Quality-Random.html)
нет recoverable status: нормальный возврат подтверждает только этот вызов, а native failure
остаётся предусловием платформы, не обещанным recoverable rejection. Ни одна проба не доказывает
будущую доступность или жёсткую календарную границу примитивов ОС. Последующие SDK entropy calls
сохраняют это предусловие квалифицированного окружения; проба не проверяет качество энтропии.

## Идентичность TLS, доверие и аутентификация

TLS явно включается для endpoint. Согласовывать TLS 1.2 или TLS 1.3 с обязательной проверкой peer, цепочки, срока действия и идентичности. Требовать выбранный вызывающим кодом PEM CA bundle, загруженный в контекст конкретного экземпляра до соединения. Отсутствующий/недоступный/невалидный материал доверия приводит к ошибке до сетевой активации. Не загружать неявные пути CA по умолчанию, `SSL_CERT_FILE`/`SSL_CERT_DIR` и не импортировать хранилища Windows автоматически. Приложение выбирает, распространяет и обновляет bundle доверия.

Использовать приватный `OSSL_LIB_CTX`, явно загруженный встроенный default provider и `SSL_CTX_new_ex`; настроить контекст до создания потоков. Ограничить байты trust bundle/число anchors и байты certificate message до разбора SDK; одна лишь глубина проверки не ограничивает разбор сертификатов. Задать конечные одобренные лимиты входных ключей/групп/подписей и консервативный объём SDK, выведенный из исходников. Deadlines handshake кооперативны между вызовами SDK и не прерывают криптографическую работу. Логические лимиты должны покрывать буферы и объекты SDK, а также пики одновременного владения старым и кандидатом; измерения сами по себе не доказывают верхнюю границу. Владельцы library context/provider/context живут дольше каждого потока и completion; Asio принимает владение переданным native `SSL_CTX`. Не менять default provider, trust store, property query или флаги инициализации процесса и не вызывать глобальный `OPENSSL_cleanup` из клиента. Свойство сборки закреплённого SDK `OPENSSL_NO_AUTOLOAD_CONFIG` отключает автоматическую загрузку конфигурации; это не утверждение об отсутствии обычной инициализации процесса OpenSSL. Системный SDK без этого свойства вне профиля. Приложение не должно вручную предварительно загружать глобальную для процесса SSL-конфигурацию `system_default`: `SSL_CTX_new_ex` может обращаться к этому реестру даже при приватном library context. Это явное предусловие для общего процесса; одного владения контекстом недостаточно для полной изоляции конфигурации. Зарегистрированные приложением пользовательские ENGINE, альтернативные key methods и внешние providers, влияющие на этот SDK, также вне профиля; встроенные пути decoder входят в его ресурсный бюджет.

Политика production TLS использует группы ECDHE `X25519`, `P-256`, `P-384`; наборы TLS 1.2 ECDHE-RSA/ECDHE-ECDSA AEAD (AES-128/256-GCM или ChaCha20-Poly1305) и TLS 1.3 AES-128/256-GCM или ChaCha20-Poly1305. Допускаются RSA-ключи размером 2048–4096 бит с открытым показателем 65537 либо EC-ключи на именованных кривых P-256/P-384; явные параметры EC и другие семейства ключей отклоняются. Выбирать RSA-PSS SHA-256/384/512, для TLS 1.2 RSA-PKCS1 SHA-256/384/512 и соответствующие подписи ECDSA P-256/SHA-256 либо P-384/SHA-384. DHE и обмен RSA-ключами не используются. Настраивать `SSL_CTX_set1_groups_list`, `SSL_CTX_set_cipher_list`, `SSL_CTX_set_ciphersuites` и `SSL_CTX_set1_sigalgs_list`, проверяя результаты. Это требования к предстоящему адаптеру production; обычный handshake осуществимости с RSA-2048 не квалифицирует каждый разрешённый или отклоняемый случай ключа.

Ограничить Certificate message размером 64 KiB и глубину проверки значением 4; PEM bundle, переданный приложением, ограничить 512 KiB и 256 anchors до разбора SDK. Проверенные буферы записи/чтения Asio имеют размер по 17 KiB; дополнительное хранилище BIO/native SSL учитывается отдельно. `SSL_CTX_set_max_cert_list` ограничивает вход разбора; `SSL_CTX_set_verify_depth` ограничивает проверку цепочки, но не предварительный разбор сертификатов. OpenSSL может декодировать открытые ключи при разборе X.509 до callback проверки сертификата. Учитывать эту начальную работу/память встроенного decoder в envelope закреплённого SDK. Политика `SSL_CTX_set_cert_verify_callback` проверяет ограничения SPKI/ключей/параметров до передачи управления `X509_verify_cert`; она не предотвращает всё более раннее декодирование ключа. Приёмка адаптера требует hostile DER, явных параметров и случаев размеров ключей, а также консервативного бюджета пиковых ресурсов/работы, обоснованного исходниками. Deadline не прерывает выполняющийся decoder. Fixture осуществимости реализует выбранные механизмы размера/глубины и обычные ключи, но не полную production-политику допуска.

Для DNS endpoint проверять непустую ASCII/A-label эталонную идентичность и отправлять SNI. Требовать совпадение SAN, отключить wildcard на части метки и не переходить к Common Name. Для IP endpoint явно проверять IP SAN и не отправлять DNS SNI. Ответы DNS/CNAME не заменяют настроенную эталонную идентичность. Проверять результат каждой настройки идентичности/доверия; пустая идентичность не может незаметно отключить проверку. [API контекста](https://docs.openssl.org/3.5/man3/SSL_CTX_new/) и [API идентичности](https://docs.openssl.org/3.5/man3/SSL_set1_host/) OpenSSL определяют эти требования.

Не выбраны обход проверки, неявный переход к plaintext, автоматическая загрузка AIA, онлайн-проверка отзыва, эмуляция политики доверия ОС, сжатие записей/сертификатов, TLS renegotiation, TLS early data, утверждение о FIPS provider, клиентские сертификаты, TLS proxy и QUIC. Развёртываниям с такими требованиями нужен явный дополнительный профиль, а не неявная отметка об успехе. Graceful shutdown TLS ограничен; timeout/abort сообщается отдельно от штатного завершения `close_notify`.

Выбранный профиль QTP-аутентификации на чтении — обычный согласованный peer, описанный в [проверке совместимости подписок](../../tests/conformance/subscriptions/VALIDATION.ru.md): передача credentials конкретному экземпляру после проверенного TLS, явная готовность/аутентификация peer, ограниченное ожидание auth и редактированная диагностика. Выбирать квалифицированное свойство QTP `authorization` с токеном `Basic`; другие схемы требуют отдельной квалификации peer. Plain TCP — отдельный явный режим без credentials. До проверки TLS credentials не отправлять; при reconnect получать credentials через callback настроенного endpoint, не записывать их в журнал и не использовать ожидающую auth-операцию другой эпохи. Состояние session auth реализуется отдельно от этого решения по TLS.

## Граница необязательной сборки и потребителя

Существующий параметр `ORG_TTLDTOR_QDCXX_BUILD_RUNTIME` по умолчанию OFF и включает только выбранную связку Asio/c-ares/Threads/native socket. Запланированная отдельная TLS-возможность также будет OFF по умолчанию, добавит OpenSSL SSL/Crypto и потребует runtime; production TLS option пока не существует. Ни одна возможность не должна менять зависимости JSON, recording, replay или чистой библиотеки. В публичных заголовках остаются стандартные/проектные типы; статический потребитель всё равно получает явную native link closure.

Операции configure/build/consumer при OFF не должны искать, получать, включать или линковать SDK runtime/TLS, запускать resolver workers, инициализировать TLS или требовать инструменты их сборки. Зависимости тестов независимо управляются `BUILD_TESTING`. Включённая сборка принимает явные проверенные корни SDK/исходников и ясно завершается ошибкой при отсутствии, неверной версии/архитектуре или несовместимом SDK. Загрузка/сборка — явный шаг разработчика, а не незаявленный побочный эффект configure.

Сохранять CMake 3.25+, C++23 и существующие toolchains/presets CLion. Передавать корни зависимостей через локальную конфигурацию, не редактируя глобальные пути. Собранные из исходников SDK с native-инструментами поддерживают MSVC x64 и Linux GCC без установленного Conan. Параметр TCP и минимальный переносимый пакет уже существуют; native linkage потребителя и install/export проверяются по [матрице TCP](../../tests/conformance/transport/TCP-VALIDATION.ru.md). Это не квалифицирует будущие TLS/package extensions или полный клиент.

## Альтернативы и последствия

| Альтернатива | Решение и причина |
| --- | --- |
| Standalone Asio и resolver на native worker | Использовать только executor/TCP: quiescence блокирующего resolver worker не ограничена публичной отменой. |
| Boost.Asio | Та же сетевая модель; дополнительная интеграция Boost не нужна для выбранной standalone closure. |
| libuv с `uv_getaddrinfo` | Его [контракт запроса](https://docs.libuv.org/en/v1.x/request.html) не позволяет отменить уже выполняемый lookup и сохраняет память запроса до завершения. Проблему времени жизни DNS не решает. |
| Непосредственные IOCP/epoll/native DNS backend | Возможная будущая работа, но требует больше платформенного кода владения и отмены, чем этот профиль. |
| Schannel в Windows и другой Linux TLS engine | Системные хранилища полезны, но две реализации TLS и две политики проверки не нужны для первого профиля. |
| Автоматические хранилища/конфигурация OpenSSL по умолчанию | Отклонить скрытый выбор доверия/конфигурации; использовать явные PEM и настройки в контексте экземпляра. |

Начальные цели квалификации — только Windows x64/MSVC и Linux x86-64/GCC. Другие ОС/архитектуры, MinGW, io_uring, альтернативные providers/allocators, поздняя несогласованная глобальная инициализация и произвольные системные SDK остаются не квалифицированы. См. [контракт проверки транспорта](../../tests/conformance/transport/CONTRACTS.ru.md): в нём отделены выполненные проверки от фактов исходного кода и перечислены необходимые проверки адаптера. По коротким loopback-пробам нельзя делать вывод о гарантиях реального времени для планирования ядром или произвольной длительности callback приложения.
