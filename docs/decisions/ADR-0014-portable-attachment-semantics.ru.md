# ADR-0014 — Переносимая семантика вложений

[English](ADR-0014-portable-attachment-semantics.md). Нормативна английская версия.

Статус: выбрана переносимая политика; независимое ревью контракта и реализация типизированных событий проверяются отдельно.

## Контекст

Закреплённый QD предоставляет вложения `Object` в Message и Configuration. Сеттеры используют
`Marshalled.forObject`; геттеры могут лениво десериализовать объект с классами приложения и
загрузчиком классов. В стандартной записи вложение имеет полный идентификатор 249 `SERIAL_OBJECT`.
Вложение Java `byte[]` само сериализуется вместе с описанием массива и длиной. Оно отличается
от тела поля с полным идентификатором 9 `BYTE_ARRAY`. TextMessage/TextConfiguration имеют
отдельный String API, а стандартное поле Text имеет полный идентификатор 10.

Текущий обобщённый C++ reader уже владеет точными nullable-телами 9/233/249 без исполнения Java
объектов. Называть такие тела декодированными Java объектами означало бы обещать отсутствующее
поведение. [Production-свидетели](../../tests/fixtures/attachments/README.ru.md) связывают различие
с реальными стандартными записями, делегатами, composer/parser callbacks и выводом FileWriter.

## Решение

Принять переносимый C++ с точными владеющими nullable-байтами сериализованного вложения и явно
выбранными зарегистрированными нативными кодеками. JVM не требуется. Получение, хранение,
копирование, сравнение и передача вложения никогда не декодируют его неявно. Исходные байты
никогда не представляются как декодированный Java Object.

[Справочник вложений](../../spec/events/ATTACHMENTS.ru.md) задаёт владение, выбор кодека, ошибки,
пределы ресурсов, время жизни callback и разделение версий. Он ограничивает последующую
типизированную реализацию; публичные имена типов и production-реестр кодеков здесь не вводятся.
Обобщённый reader остаётся доступен по своим существующим контрактам полей и профилей.

В QD wire не вставляются идентификатор кодека, заголовок, оболочка или новый формат payload.
Приложения согласуют представление и выбирают кодек через явную локальную конфигурацию.
Версии формата кодека отделены от версии события Configuration. Текстовые варианты сохраняют
независимый контракт nullable String.

## Альтернативы

- JVM bridge может дать загрузку классов и совместимость с произвольной Java-сериализацией.
  Ему нужен отдельный контракт runtime, развёртывания, ресурсов и безопасности; этот путь не выбран.
- Нативное декодирование конечного списка Java-классов допустимо как явный кодек. Оно не обещает
  совместимость с произвольным `Object` и не превращает неизвестный payload в известное значение.
- Автоматическое распознавание формата сделало бы декодирование неявным и неоднозначным; оно исключено.

## Последствия и совместимость

Приложение, которому нужна семантика Java объекта, должно предоставить совместимый явный кодек
или использовать отдельно спроектированный bridge. Неизвестные классы, повреждённая
Java-сериализация и даже engaged-empty тело могут быть корректными полученными opaque-данными.
Позднее явное декодирование может завершиться ошибкой без потери данных. Null отличается
от engaged-empty и сериализованного пустого Java-массива.

Фильтрация версий Configuration остаётся ответственностью реализации получения и выбранного
контракта. Декодирование payload не принимает и не отклоняет события и не продвигает состояние
их версий. Грамматика wire, идентичность схемы, прежние пределы и поддержка исходящих полей не меняются.
